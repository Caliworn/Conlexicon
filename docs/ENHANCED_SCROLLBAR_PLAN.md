# 增强滚动条计划

状态：设计草案，已于 2026-11-09 独立复评（结论见第 9 节），第 1a 批、S12 与 1b 已实装（2026-11-09），1c 未实施；第二期词根模式的方案见第 11 节（2026-11-16 起草，用户同日确认），2a 与 2b 均已实装（2026-11-16）。第 2 节是用户于 2026-11-09 确认的决定，其中 D6–D14 是用户试用交互原型后定下的；第 4–8 节是代理起草、经复评修正的方案；第 7 节列出其中代理自己拟定、尚待用户确认的选择。

交互原型：仓库根目录的 `scrollbar-prototype.html`，由开发服务作为公开静态文件提供（与 `control-gallery.html` 相同），打开 `/scrollbar-prototype.html` 即可。它用产品样式表和模拟数据重现分窗加载与高度测量，默认值即第 2 节的决定，其余选项用于对照。原型是开发期间的临时夹具：1b 验收通过后，在同一次提交中删除该文件，以及 `lib/static-server.js` 公开清单和 `scripts/check-http-access.js` 入口页集合中的对应条目。

本计划接续 2026-07-06 交接文档中的“增强型滚动条／词典地图”设想（原文见提交 `7f2ee3c`，后在精简交接时删除），并取代 [SQLite 后端规范](SQLITE_BACKEND_SPEC.md) 第 11 节中对应的暂缓项。

## 1. 目标与边界

在词条列表右侧用自定义导航条取代原生滚动条：拖动跟手、显示当前排序的分段索引、可以直接跳到某一段。

当初暂缓这个功能，是要等后端稳定提供结果总数和随机窗口读取。这两样现在都已具备（见第 3 节），所以它现在只缺设计，不再受后端限制。

本计划不做：

- 位置标记：不标当前词条（详情里已有定位按钮）、质量问题、搜索命中或书签。
- 与当前排序无关的索引，例如按词形排序时显示日期索引。
- 自定义字母表排序（见第 10 节）。
- 语料列表和质量页列表（见第 10 节）。词根模式是第二期，方案见第 11 节。
- 功能结果和质量结果筛选下的分段索引：这两种筛选只显示滑块（见 5.3）。
- 键盘跳到指定分段的快捷键。
- 自己实现一套滚动系统：滚动仍由原生滚动容器完成。

## 2. 已确认的决定（用户，2026-11-09）

- **D1 索引只跟随当前排序。** 旧设想中“拖动时指针左偏显示首字母、右偏显示日期”的做法推翻。原因：按词形排序时日期是乱序的，跳到某个日期找不到连续的位置；而且这种手势很难被发现。
- **D2 隐藏原生滚动条。** 导航条和原生滚动条计算位置的方式不同（见 5.1），两者同时显示时会对不上。
- **D3 不做位置标记。**
- **D4 第一期只做词条列表的普通模式（含搜索和筛选）**，词根模式放到第二期。
- **D5 自定义字母表排序一定会做，但不必现在做。** 本计划不依赖它，只预留接口约束（5.4）。
- **D6 刻度门槛 100 条。** 结果少于 100 条时只有滑块和气泡，没有刻度，刻度栏也隐藏。
- **D7 抓手平时细，悬停或拖动时变宽**，变宽后 14px，最小长度 32px。
- **D8 刻度栏悬停或拖动时浮出**，盖在卡片上，不占列表宽度；刻度字号 13px。
- **D9 气泡显示分段名和序号**（如“k”和“3,930 / 10,000”）。
- **D10 拖动中指针停住 50ms 后才请求窗口。**原定 120ms，用户在产品中试用后于 2026-11-09 改为 50ms。
- **D11 刻度放不下时合并**相邻小段（显示为“a–c”）；**时间分段粒度自动**：跨度 60 天内按日，4 年内按月，更长按年。
- **D12 点轨道空白处按比例跳转，点刻度精确跳到该段第一条。**
- **D13 列表处于“正在更新”时，导航条随列表一起变淡。**
- **D14 取消滚动期间的高度修正延迟**，改为渲染后立即测量并按下标对准，同时关闭该列表的浏览器滚动锚定（5.8）。用户在原型中用真实滚轮对比新旧两种做法，没有感觉到顿挫。
- **D15 导航条设为 `aria-hidden`，不占 Tab 停靠点，不提供键盘操作**（原 S7），与原生滚动条相同。
- **D16 液态玻璃下导航条用 CSS 材质，不注册光学表面**（原 S8）。
- **D17 悬停预览**（原 S13）：指针沿轨道移动、未拖动时，气泡显示点下去会跳到哪一段和第几条；触屏不触发。
- **D18 刻度最小间距 20px**（原 S14），实际至少一行字高。
- **D19 刻度栏宽按当前最宽的标签自动计算**（原 S15），加 8px，不设固定宽度。
- **D20 刻度栏整栏分块点击**（原 S16）：每个刻度占满栏宽。每块的上下范围就是这一段在轨道上实际占的范围，从本段起点到下一个刻度的起点，第一块和最后一块延伸到栏的两端；标签放在块的中间。最初按“上下延伸到与相邻刻度的中点”实装，点击范围比实际段整体偏上半段，用户试用后指出不直观，于 2026-11-09 改为现在的规则（标签居中是代理的选择）。合并规则保证除最后一块外每块至少 20px；最后一块延伸到栏底，最矮只有半个抓手，矮于 20px 时并入上一组。
- **D21 功能结果和质量结果筛选下只显示滑块**（原 S9），不显示刻度和气泡。
- **D22 时间分段按用户本地时区划分**（原 S10）。
- **D23 触屏快速拖动手柄从 1b 拆出，单独作为 1c**；S6（手柄停下后多久隐藏）到 1c 再定。（用户，2026-11-09）

词根模式（第 11 节），用户于 2026-11-16 确认代理拟定的 S17–S22：

- **D24 定位单位用估算高度**（原 S17，11.2）。
- **D25 气泡显示词根的分段名加组序号**（如“k”和“37 / 1,204 组”）；全部展开或搜索时，未加载窗内的组序号是近似值（原 S18，11.6）。
- **D26 刻度门槛沿用 100，按组数算**（原 S19）。
- **D27 分 2a（抓手）和 2b（分段）两批**（原 S20，11.7）。
- **D28 不做“窗口加载时按结果下标恢复位置”**，2a 实测落点误差超过一行再补（原 S21，11.4）。
- **D29 搜索或排序变化后，手动展开记录的组下标待该组重新加载时重记**，其间总量可能有一次变化，不为此增加后端查询（原 S22，11.3）。

## 3. 现状（2026-11-09 对照代码确认）

- 词条列表是自定义虚拟列表（`app.js` 的 `createVirtualListState`、`renderVirtualListWindow`），每行位置由各行高度累加得出。没量过的行用估算高度（词条卡片 145px），渲染后用 ResizeObserver 量真实高度。滚动期间（停下后 180ms 内都算）不应用新量到的高度，窗口渲染每 50ms 最多一次。
- 普通列表每窗 200 条，最多保留 5 个已加载窗。未加载的窗用“条数 × 估算高度”的占位撑开，原生滚动条因此代表完整结果集。可见范围变化时，加载可见的窗及其前后各一个窗（`handleEntryQueryWindowRange`）。
- 词条列表的数据有三种来源：`GET /entries`（搜索与结构筛选），以及功能结果和质量结果筛选（`POST /analysis/features/query`、`POST /quality/query`）。三者都按窗口读取。
- 后端：`windowCursor` 加 `windowOffset` 可读取任意位置的窗；`/entries/:id/location` 返回词条在当前结果中的下标；结果总数在 `pageInfo.total` 中。带搜索的查询会话保存完整的有序命中 ID（`orderedIds`）；不带搜索时直接用 SQL 分页。
- 排序只有词形、修改时间、创建时间三种，各分正序和倒序。词形排序键 `sort_key` 是词形去掉首尾空白再转小写（`normalizeText`），以 BINARY 比较，等于按码位排序；没有自定义字母表。
- 新建词条的 `createdAt` 由 `new Date().toISOString()` 生成；旧 JSON 导入时按原字符串保留，不校验格式。
- 原生滚动条没有自定义样式，明暗由各皮肤的 `color-scheme` 决定。`.entry-list` 以 `padding-right: 4px` 给滚动条留出空隙。
- `renderVirtualListWindow` 每次渲染都会删除容器中不属于当前窗口的子元素，所以导航条不能放进列表容器内部。
- 词条列表本身没有处理滚动按键；方向键和 PageUp/PageDown 由浏览器滚动最近的可滚动容器。
- 三套皮肤的词条列表使用同一布局（2026-11-09 起；此前只有液态玻璃使用 mail 布局）。

拖动原生滚动条不跟手，原因是：它按像素换算位置，而像素来自估算高度和占位高度，量出真实高度后总长会变。2026-07 已做过几轮缓解，目前是否仍明显不跟手，没有重新测过。导航条按条目下标定位（5.1），可以绕开这个问题。

## 4. 功能

1. 竖向细线轨道加胶囊抓手。抓手长度 = 可见条数 ÷ 总条数，最小 32px；平时细，悬停或拖动时变宽到 14px（D7）。可点击区域比可见抓手宽。
2. 拖动时抓手紧跟指针，列表随后跟上；松手后抓手按列表实际位置重新同步，列表不再跳动。点击轨道空白处按比例跳转，并可接着拖动（D12）。指针停在导航条上时，滚轮照常滚动列表。
3. 拖动时左侧浮出气泡，显示目标位置的分段名和序号（D9）：词形排序显示首字母，时间排序显示年、月或日。气泡叠在列表上方，不挤占布局。
4. 指针移到导航条上或开始拖动时，刻度栏浮出，盖在卡片右侧（D8）。刻度字号 13px，相邻刻度至少相隔一行字高；放不下时合并相邻小段（D11）。整条刻度栏按刻度切成上下相接的块，每块占满栏宽，范围就是这一段在轨道上的实际范围（与悬停预览、拖动用同一换算），标签放在块的中间；悬停整块高亮并提示段名和条数，点块内任意位置精确跳到该段第一条（D12）。
5. 时间排序按结果的时间跨度自动选择以年、月还是日分段（D11）；没有日期或日期无法识别的词条归入单独一段。
6. 由导航条接管的列表（第一期即普通模式）始终隐藏原生滚动条，只要能滚动就显示导航条；结果少于 100 条时只有抓手和气泡，没有刻度，刻度栏也隐藏（D6）。始终隐藏可以避免原生滚动条时有时无、导致列表宽度变化和卡片全部重新量高。词根模式在第一期不接管，保留原生滚动条。
7. 列表处于“正在更新”时，导航条随列表一起变淡（D13）。
8. 三套皮肤各定义颜色 token，支持明暗主题、减少动态效果和强制高对比。液态玻璃下用 CSS 材质，不注册光学表面。
9. 触屏（窄屏列表抽屉）保留原生惯性滚动；开始滚动时显示快速拖动手柄，停下后自动隐藏。触摸命中区域至少 44px 宽，可见滑块可以更细。

## 5. 技术方案

### 5.1 按条目下标定位

- 滑块位置 = 可见区第一条的结果下标 ÷ 总条数。可见位置落在占位块内时，按它在占位块中的高度比例换算成下标。
- 拖动时，由指针位置算出目标下标，再换算成 `scrollTop`：目标已加载时取它的真实行位置；目标仍在占位中时，按同一比例换算出位置。
- 不变量：在同一份布局状态下，“`scrollTop` → 下标”和“下标 → `scrollTop`”互为反函数。这样只要拖动期间布局没变，松手时从列表算出的下标就是指针给出的下标，滑块不会回跳。该不变量须有测试。
- 拖动期间滑块只跟指针走，不读 `scrollTop`；松手后只把滑块同步到列表的实际位置，不移动列表。窗口加载后的高度修正由现有锚点逻辑保持可见内容稳定。
- 点刻度是离散跳转，必须落在该段第一条：先滚到估算位置，等所在窗加载完成，再用现有的 `scrollVirtualListItemIntoViewStable` 对准。点轨道空白处只按比例跳转，不做精确对准。
- 量到真实高度和占位被替换都不会让滑块跳动。前者由 S12 在绘制前按视口顶部那一条对准；后者是因为普通模式给每张未测高的卡片同一个估算值（145px），窗口加载时整页按原占位高度缩放，页内条目的分布与占位块内的均匀换算完全一致，所以拖到未加载窗口时，加载前后同一滚动位置对应同一条，落点就是目标那一条，松手时滑块只有亚像素的移动（1 万条实测 0.001–0.019px）。原先按卡片类别分别估算，页内分布与占位块不一致，会让落点差几条，2026-11-09 改为统一估算并删除分类估算。被淘汰后重新加载的窗口里，量过的卡片直接用缓存的真实高度，页内分布不再均匀；实测 1 万条压力词典中拖回这样的窗口（200 张里 88 张用真实高度，113–166px、平均 146.8px），落点与目标相差 −0.16 和 +0.29 条，与从未加载过的窗口一样准，因为高矮随机穿插、累计误差互相抵消。同一页内卡片高矮成片分布（如前半页长、后半页短）时，理论上仍可能差几条，压力词典没有这种分布，未测到。可选的后续改进：窗口加载、占位被替换时按视口顶部的结果下标恢复位置，而不是按行 key（占位行的 key 加载后就不存在），这样任何高度分布下落点都准。另一个代价是用滚轮滚动时，滑块按经过的条数移动，词条高矮不一时速度略有起伏，一屏内通常可以平均掉。

### 5.2 拖动时的加载

- 拖动期间每帧最多更新一次 `scrollTop`；指针停住一小段时间或松手后，才交给现有的按可见范围加载逻辑去请求窗口。
- 迟到的旧响应由现有请求编号丢弃；“最多保留 5 个窗”的上限保证快速拖过大词典时不会全部加载。

### 5.3 概览接口

```text
GET /api/dictionaries/:id/entry-overview?<与 /entries 相同的查询参数>&tz=<IANA 时区>
→ { total, sort, buckets: [{ label, start, count }] }
```

- 计算方式：按当前排序取出全部结果的分段键序列，在 JS 中按“相邻且键相同”切段。带搜索时，用查询会话中的 `orderedIds` 读取对应的键；不带搜索时，用与列表相同的筛选条件和 `sqlOrderClause` 排序，在 SQL 中只读出分段键。不用 `GROUP BY` 加前缀和：那要求同一个键的结果必然连续，而导入的非 ISO 日期等情况下不能保证；按顺序切段时，即使同一个键分成两处，也只是出现两段，起点仍然正确。
- 服务端不缓存结果；前端按查询 key（含词典版本）缓存，查询条件或词典版本变化后丢弃，下次悬停再请求。
- 时间分段按用户本地时区划分，前端传 IANA 时区名。服务端先算出各段在 UTC 下的边界，再与时间戳字符串比较，避免逐行做时区格式化。没有日期或日期无法解析的词条归入“无日期”段。
- 指针第一次移进导航条时才单独请求（实装时由代理改定：刻度和气泡只在悬停或拖动时出现，不碰导航条的用户不必请求），按查询 key 缓存，不并进首窗响应。少于 100 条的结果也要请求，因为气泡仍需要分段名（D6）。请求失败时抓手照常可用，只是没有刻度和气泡文字。
- 路径为独立的 `/entry-overview`，不放在 `/entries/` 下：导入的词条 ID 格式不受限，最初放在 `/entries/overview` 时会截走 ID 为 `overview` 的词条（2026-11-09 审计发现后改正）。
- 第一期只覆盖 `GET /entries` 的结果。功能结果和质量结果筛选也按窗口读取，导航条仍可按下标显示滑块，但没有分段索引；是否以后补上，取决于那两条查询路径能否以较低成本给出有序结果的分段键。
- 实装时同步写入 `docs/API_CONTRACT.md`。

### 5.4 排序单位：与排序共用一个函数

分段使用的“首字母”必须来自排序本身的切分规则，不由导航条自行决定。实现上提供一个共享函数，返回词形的第一个排序单位：

- 现在：`normalizeText` 后的第一个码位，与当前码位排序一致。限制是 `ng` 这类二合字母、NFD 形式的组合附加符号不能作为一个字母。
- 自定义字母表排序落地后：改为按字母表切出的第一个字母。届时 `sort_key` 很可能会变成按字母序号编码的排序键，从中截出的第一个字节不再是可读字母，所以不能依赖 `sort_key` 的原始内容。

按码位分段会把当前排序的问题直接摆出来：带附加符号的字母（如 `é`）排在 `z` 之后，以标点或数字开头的词形各成一段，IPA 字符多的词形会切出很多段。这是现有排序的行为，不是导航条的缺陷，也正是需要自定义字母表排序的理由之一。

### 5.5 隐藏原生滚动条

- 对导航条接管的列表使用 `scrollbar-width: none`（Chromium 121 起支持；桌面外壳 Electron 31 为 Chromium 126）。这样只是不画滚动条，滚动容器不变：滚轮、触控板、触摸惯性、Windows 中键自动滚动和键盘滚动都继续由浏览器处理，虚拟列表与锚点恢复只读写 `scrollTop`，也不受影响。
- 导航条是列表容器的兄弟元素，叠在其右侧。指针停在导航条上滚动时，滚轮事件到不了列表，需要转发：用非被动监听器取消默认行为（否则外层可滚动的祖先也会跟着滚），再用 `scrollBy` 转给列表，并按 `deltaMode` 把行、页单位换算成像素。
- `.entry-list` 的 `padding-right: 4px` 改为给导航条留出的位置。
- 导航条设为 `aria-hidden`，不占 Tab 停靠点，与原生滚动条的待遇相同；键盘和读屏用户仍通过列表内容和容器滚动来导航（读屏行为是推断，需实测）。

### 5.6 与列表状态同步

- 查询条件变化、列表处于“正在更新”（旧内容变淡）期间，导航条保持旧状态并随列表一起变淡；新首窗提交后，丢弃旧概览（用请求编号区分）并按需重新请求。
- 保存词条后查询缓存 generation 变化，概览随之失效；只在导航条需要显示刻度时才重新请求，不在每次保存后主动计算。

### 5.7 数据来源接口

导航条通过 `total`、`indexAtScroll()`、`scrollToIndex()`、`overview()` 四项读取数据，不直接访问词条查询状态。第一期只实现词条列表这一个来源，不为语料列表和质量页列表预先适配；接入第二个来源时再按需要调整接口。

### 5.8 卡片高度修正（原型发现，已确认为 D14）

现行虚拟列表在滚动期间（停下后 180ms 内）不应用新量到的卡片高度，停下后再统一修正并恢复锚点。这样做是为了不在拖动原生滚动条时扰动滑块。原型照搬这套做法后，复现了“鼠标滚轮往上滚时列表上下闪”：上方新出现的卡片按真实高度排版，位置表仍是估算值；浏览器自带的滚动锚定先补偿一次，停下后手动锚点又按旧位置表再修正一次。往下滚时新卡片出现在视口下方，不影响可见内容，所以没有问题。一段区域滚过一次后高度已缓存，所以不容易复现。脚本测试（1 万条、从中段往上连续滚 120 步）中有 40 步内容位置不对，最多偏差约 100px。

导航条按下标定位，原生滚动条也已隐藏，延迟修正的理由就不存在了。原型改为：渲染后在绘制前立即测量，按测量前的位置表记下当前下标，更新高度后立即对准回去，并对该列表关闭浏览器自带的滚动锚定（`overflow-anchor: none`），避免重复补偿。同一测试中上下滚动的偏差均为 0，点刻度和拖动松手仍准确落位。

- 这是对现行虚拟列表核心逻辑的改动，不只是加导航条。产品的词条列表用的是同一套延迟修正，推测也有同样的向上滚动闪动，但没有在产品中验证。
- 风险：滚轮平滑滚动进行中用程序设置 `scrollTop`，可能打断浏览器的平滑滚动动画，造成顿挫。脚本无法验证，须用真实鼠标滚轮和触控板确认。

### 5.9 渲染开销

整个控件只有轨道、滑块和有限数量的刻度标签。滑块用 `transform` 移动；滚动时除了读 `scrollTop` 不读布局。

## 9. 复评记录（2026-11-09）

把第 4–8 节当作外部提案重新检查后的结论。

**保留**

- 按条目下标定位：只要刻度按比例摆放，就必须用这种方式，否则刻度和滑块会随高度估算漂移。
- 概览单独请求：并进首窗会拖慢首屏，而且只有显示刻度时才需要。前端只保留 5 个窗，自己算不出分段，所以必须由后端提供。
- 导航条放在列表容器外并转发滚轮：放进容器就得改虚拟列表的核心渲染。转发只需要很少的代码。

**修正**

- 原方案“松手后精确对齐”会让列表在松手时跳一下。改为松手只同步滑块，精确对准只用于点刻度（5.1）。
- 原方案“原生滚动条始终隐藏”没有考虑第一期不接管的词根模式，那样词根模式会完全没有滚动条。改为只在导航条接管的列表上隐藏（第 4 节第 6 条）。
- 原方案用 SQL 窗口函数分组，前提是同一个键的结果必然连续，导入的非 ISO 日期等情况下不能保证。改为按顺序切段（5.3）。
- 补上原方案遗漏的几项：词条列表的三种数据来源（5.3、S9）、时间分段的时区和无日期段（5.3、S10）、滚轮转发须阻止祖先容器跟着滚（5.5）、与“正在更新”状态的同步（5.6）、液态玻璃的 mail 布局（第 8 节）。
- 原方案的“通用组件”收窄：第一期只实现词条列表一个来源（5.7）。
- 拆成 1a 和 1b 两批（第 6 节）。

**考虑过、未采用的替代**

- 保留原生滚动条，另加一列等距排列的字母索引（类似手机通讯录）：不必隐藏滚动条，也不必转发滚轮，成本最低。没有采用，原因有二：等距排列不反映各段大小和当前位置；时间排序下段数多，等距排列放不下。

**风险**

- 1a 自身的收益（拖动跟手）以“原生滚动条仍明显不跟手”为前提，这一点自 2026-07 的缓解后没有重新测过。1a 主要是 1b 的基础。

## 11. 词根模式（第二期）

状态：代理于 2026-11-16 起草并独立复评（11.9），用户同日确认（第 2 节 D24–D29）。2a 与 2b 均已于 2026-11-16 实装。11.1 是 2a 实装前对照代码确认的现状，其中标了“（2a 已改）”的各条已不是现行行为，最后一条“没有概览接口”也已由 2b 补上；11.2–11.8 是方案。

### 11.1 现状（2026-11-16 对照代码确认）

- 词根组按词根自身的当前排序排列，组内衍生词用同一排序（`rootTopologyGroupsForSort`）。后端查询会话保存全部组及各组的衍生词 ID（`session.groups`）。
- 每窗 100 组，最多保留 5 个已加载窗。首窗和定位响应带 `pageInfo.windowMetrics: [{ groupCount, derivedCount }]`，前端据此估算未加载窗的高度（`rootGroupWindowMetricHeight`）。
- 行高估算（2026-11-10 列表改版后）：未展开的词根卡 145px；展开的词根卡 137px；衍生行 44px，组内最后一行 57px。即展开 n 个衍生词的组合计 150 + 44n，比未展开时多 5 + 44n。衍生行高度由样式固定，实测与估算一致。
- （2a 已改）未加载窗的估算是 `groupCount × 145 + derivedCount × 44`，只在“全部展开”或搜索时计入衍生词，并且漏掉每个展开组多出的 5px。手动展开且未搜索时不计衍生词。
- （2a 已改）搜索时只有“有衍生词命中”的组自动展开，但 `derivedCount` 把“只有词根命中”的组的衍生词也算了进去，手动模式下搜索时未加载窗的占位偏高。全部展开模式下搜索时所有带衍生词的组都展开，`derivedCount` 是对的。
- （2a 已改）展开状态是两个按词根 ID 的集合（手动展开、全部展开模式下的手动收起）加一个模式标记，切换搜索或排序时不清空，只在“全部收起”和切换词典时重置。窗口被淘汰时，占位高度取该窗各行当时的实测像素高度（`queryWindowPageHeight`），展开信息只以像素形式留下。
- 窗口加载时位置靠保持高度稳住：加载前读取占位的当前高度，加载后整窗各行的估算按“占位高度 ÷ 自然估算高度”缩放（`preserveQueryWindowPageHeight`），所以滚动位置不变时同一像素处还是原来那一行。`renderVirtualList` 另按行 key 恢复锚点，锚点行不存在时保持 `scrollTop` 不变。
- 衍生词按组整组加载，请求在词根行或占位行渲染时发出（`startRootGroupDerivedLoad`）。加载前是一个高度为 13 + 44n 的占位行，加载后换成 n 行，合计高度相同。
- （2a 已改）导航条拖动期间的加载暂停只在普通模式的 `handleEntryQueryWindowRange` 里检查；`handleRootGroupsWindowRange` 和衍生词请求不检查。
- （2a 已改）词根模式仍用原生滚动条和滚动期间延迟的高度修正（`immediateSizeUpdates` 为 false）；列表上下渐隐为原生滚动条保留了一层不透明遮罩和宽度测量。
- 没有词根模式的概览接口。

### 11.2 定位单位：估算高度

导航条的“下标”在词根模式下取每一行的估算高度：未展开的词根卡 145，展开的词根卡 137，衍生行 44（组内最后一行 57）。实测高度不参与。普通模式是它的特例：每条词条的权重相同，所以与按条数定位等价。

估算会读取当前展开状态：展开或收起一个组、点“全部展开／全部收起”都会改变总量，抓手的位置和长度随之变化，这与内容变长时原生滚动条的表现一致。卡片量出真实高度不改变权重，抓手不漂。

没有采用的两种单位：

- **组下标**：滚过一个展开了 300 条衍生词的组（约 13,200px）时抓手不动，拖动也到不了组内。
- **行下标**（词根卡和衍生行各算 1）：词根卡 145px、衍生行 44px，滚过词根卡时抓手比滚过衍生行慢三倍多；窗内各行的分布与占位的均匀换算也对不上，拖到未加载窗会差几行。

按估算高度定位时，未加载窗的占位在权重上是均匀的，加载后各行未测高时像素位置与权重一一对应，所以拖到未加载窗时，加载前后同一滚动位置对应同一行。这与普通模式靠统一估算得到的性质相同。

### 11.3 布局与权重

- 导航条读的布局改为：每个虚拟行一项，`count` 是该行的权重，`start` 是之前各行权重之和；`offsets` 仍是虚拟列表的实测像素位置。已加载的行直接用虚拟列表已有的估算高度（`item.estimatedHeight`）；窗口占位行用该窗的权重。`lib/list-navigator.js` 的两个换算函数对非整数的 `count` 本来就成立，不用改。
- 未加载或已淘汰窗的权重由窗口指标按当前展开状态算出，不取实测像素：

  ```text
  权重 = groupCount × 145 + 展开组数 × 5 + 展开组的衍生词数 × 44
  ```

  | 状态 | 展开组数 | 展开组的衍生词数 |
  |---|---|---|
  | 全部展开（搜索与否） | `derivedGroupCount` | `derivedCount` |
  | 手动模式、搜索中 | `matchedGroupCount` | `matchedGroupDerivedCount` |
  | 手动模式、未搜索 | 0 | 0 |

  再按展开记录（见下）加上手动展开的组、减去手动收起的组。占位的像素高度沿用现状（淘汰时取实测），只有权重改用这个公式。
- `windowMetrics` 每窗补三个数（后端在已有的循环里统计，不需要新查询）：`derivedGroupCount`（有衍生词的组数）、`matchedGroupCount`（有衍生词命中的组数）、`matchedGroupDerivedCount`（这些组的衍生词总数）。未搜索时后两个等于 `derivedGroupCount` 和 `derivedCount`。未加载窗的像素估算同时改用上面的公式，搜索时不再偏高，窗口加载时的缩放系数回到 1。
- 展开记录：两个 ID 集合改为 `词根 ID → { 组下标, 衍生词数, 命中衍生词数 }` 的表，在组处于已加载窗时写入。组下标只对写入时的查询有效：搜索或排序变化后，记录保留展开意图，组下标待该组在新查询中加载时重记；在此之前它所在的未加载窗权重少算或多算这一组，加载后总量变化一次。这是已知的不精确，不为它增加后端查询。

### 11.4 加载与高度修正

- 拖动期间的加载暂停扩展到词根窗口（`handleRootGroupsWindowRange`）和衍生词请求。现在这两处不受控：全部展开时拖过大段列表，每个经过视口的展开组都会发一次请求，在同步执行的服务端排队。指针停住 50ms 或松手后，对当时可见的窗口和展开组补发。
- 词根模式启用渲染后立即测高并按行对准（D14 的做法），对列表关闭浏览器滚动锚定，与普通模式一致。
- 不做“窗口加载时按结果下标恢复位置”（5.1 末尾的可选改进）。核对加载路径后的理由：
  - 窗口加载：权重与未测高的像素位置一一对应（11.2），不依赖下标恢复。
  - 衍生词加载：占位行与加载后的各行合计高度相同、每行等高，占位行消失后 `scrollTop` 不变，同一像素处就是目标行。
  - 剩下的误差来源只有“被淘汰后重新加载的窗里，量过的词根卡直接用缓存的真实高度”，与普通模式相同；普通模式实测差不到一条。
  - 它改的是虚拟列表的公共路径，普通模式已验收的落点要重测，并且在窗口加载时用程序设置 `scrollTop`，可能打断进行中的滚轮平滑滚动。
- 2a 验收时在词根模式实测落点误差（全部展开、搜索自动展开、拖回已淘汰的窗三种情况）。超过一行再补这一批，排在 2a 与 2b 之间，并先在普通模式对照已有基线。2a 实测（2026-11-16，1 万条压力词典、8,147 组，13 个位置）：未测高时相差 0–0.5，测高后最多 29，单位同像素，都不到一条衍生行（44），所以不补。实装中另发现首窗加载时把列表上一个状态的高度当成占位高度来缩放，已随 2a 修正（见 `CHANGELOG.md`）。

### 11.5 概览接口

```text
GET /api/dictionaries/:id/root-group-overview?<与 /root-groups 相同的查询参数>&tz=<IANA 时区>
→ { total, sort, grain, buckets: [{ key, start, count, derivedCount, derivedGroupCount, matchedGroupCount, matchedGroupDerivedCount }] }
```

- 按词根自身的分段键（词形排序取第一个排序单位，时间排序取年、月或日）把会话中的全部组按顺序切段，复用 `lib/entry-overview-model.js`。`start` 和 `count` 以组为单位；后四个数是本段各组的合计，与 `windowMetrics` 同义。
- 前端把每段的起点换算成权重：之前各段按 11.3 的公式累加，再按展开记录中组下标小于 `start` 的项修正。展开状态变化后重新换算并更新刻度，不重新请求。
- 请求时机、缓存和失效规则与普通模式的概览相同（5.3、5.6）：指针第一次移进导航条时请求，按查询 key 缓存。
- 路径不放在 `/root-groups/` 下，理由同 5.3：该前缀下已有以词根 ID 为路径段的衍生词接口。
- **实装时发现并改正**：11.1 第一条说词根组“按词根自身的当前排序排列”，起草时没有核对排序函数。词根组原来用 `localeCompare("zh-CN")`，普通模式用 `sort_key` 的码位顺序，不是同一个排序，5.4“分段单位来自排序本身”没有满足：带附加符号的字母与基础字母交错，1 万条压力词典切出 567 段（普通模式 21 段）。用户 2026-11-16 选定把词根组的排序改成与普通模式相同（`compareEntryRecordsInSqlOrder()`，`sqlOrderClause()` 的内存版本），没有采用“保持排序、分段按排序的字母归并规则”。改后两种模式都是 21 段。以后做自定义字母表排序时，这两个函数和 `firstSortUnit()` 一起改。

### 11.6 导航条组件的改动

- 气泡的序号文字改由调用方根据位置生成，组件不再假定“下标 = 条数”。普通模式照旧显示“3,930 / 10,000”；词根模式显示组序号（如“37 / 1,204 组”）。
- 位置换算成组序号：位置落在已加载的行时取该行的组下标，是精确的；落在未加载窗的占位内时按比例估。手动模式下占位内各组权重相同，估算是准的；全部展开或搜索时各组衍生词数不同，序号是近似值，指针停住、窗口加载后变为精确。分段名不受影响，各段起点可以精确换算。
- 刻度门槛（D6）改由调用方给出用于比较的数量，词根模式按组数算。
- 点刻度时把分段本身交给调用方。词根模式按该段的起始组下标精确对准：先滚到估算位置，等所在窗加载完成，再对准该组的词根行，做法与普通模式的 `alignEntryListJump` 相同。

### 11.9 复评记录（2026-11-16）

把 11.2–11.8 当作外部提案重新检查后的结论。

**保留**

- 估算高度作为定位单位。它是普通模式做法的推广，组件的换算函数不用改，落点性质与普通模式相同。
- 概览单独请求、按查询 key 缓存，与普通模式一致。

**修正**

- 初稿要求去掉衍生词占位行 key 中的加载状态，理由是加载后按 key 的锚点会失效。核对后撤回：占位行消失时 `scrollTop` 保持不变，而占位与加载后的各行合计等高，位置本来就不动。
- 初稿把“按结果下标恢复位置”当作可能的前置批次。核对加载路径后改为不排期、以 2a 的实测结果为触发条件（11.4）。
- 初稿让未加载窗的权重在淘汰时取快照。改为统一由窗口指标和展开记录算出，2b 换算刻度位置时用同一份数据，不会出现两套数字对不上。

**考虑过、未采用的替代**

- 自绘抓手直接镜像 `scrollTop ÷ scrollHeight`：不需要后端改动。没有采用，因为卡片测高后总高会变，抓手会漂，刻度也无法稳定摆放，正是第一期要绕开的问题。
- 概览返回每组的衍生词数，让组序号在未加载窗内也精确：1 万组约 40KB。没有采用，近似只出现在全部展开或搜索时的未加载窗内，停住 50ms 后即变精确。

**风险与未确认**

- 词根模式是否也有“向上滚动时列表上下闪”（5.8）是推断，没有在产品中验证；立即测高在词根模式下的表现要到 2a 才能确认。
- 搜索或排序变化后，展开记录的组下标暂时失效（11.3），带来一次总量变化。实际是否察觉得到，未测。
- 以上现状核对读的是窗口加载、锚点恢复、展开与淘汰的代码，没有运行验证。
