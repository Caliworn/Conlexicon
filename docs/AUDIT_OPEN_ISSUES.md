## 1. 保存与数据一致性

### A02：并发读改写 `index.json` 会丢词典登记或覆盖其他更新

- **现状**：新建／导入、删除、激活和偏好更新各自读取 `index.json`，修改后写回，没有统一的串行读改写机制。
- **影响**：两个请求都返回成功，但后写入的旧索引会覆盖前一个请求的登记或偏好。SQLite 文件仍在，词典却不出现在正常入口。
- **证据**：此前临时 SQLite 测试连续八组并发创建，都出现“两次成功，索引只增加一个词典”。当前 `importDictionarySnapshot()` 仍是先提交数据库，再读 index 并写回（约 601–605 行）。
- **定位**：`lib/sqlite-dictionary-repository.js` 的 `importDictionarySnapshot()`、`writeIndex()`（约 3779 行）及所有修改索引的调用方。
- **处理方向**：把整个“读当前值 → 修改 → 写回”放进同一个串行边界；只串行文件写入不足以防止丢更新。与 A03 一起设计。

### A03：索引文件非原子写入，SQLite 与索引登记没有共同事务

- **现状**：`writeJson()` 直接写目标文件（约 3832 行）；导入先提交 SQLite，再登记 index。
- **影响**：
  - 写入中断可能留下截断的 index；
  - 数据库成功而 index 失败时，可能留下未登记的数据库，或者报失败但已有数据库已被改动。
- **证据级别**：写入顺序和缺少原子替换已由代码确认；断电、磁盘满等失败点的实际后果尚未做故障注入，不要写成已发生事故。
- **处理方向**：原子文件替换与 A02 的串行读改写一起设计，并补上“数据库提交后登记失败”的恢复路径。不需要因此把全局索引迁入 SQLite。

### A04：docs＋corpus 联合自动保存可能部分提交

- **现状**：`POST /api/dictionaries/:id/autosave` 依次调用 `saveDocs()` 和 `saveCorpusChanges()`，两者各自开启并提交事务（`lib/api-routes.js` 约 144–163 行）。
- **影响**：docs 成功而 corpus 失败时，请求报错但 docs 已保存，结果既不是全部成功，也不是全部失败。
- **证据级别**：路由和事务边界已确认；日常界面是否显示错误状态不能仅由此推断。该端点也用于退出时的 beacon／keepalive 保存，验收需覆盖这种调用方式。
- **定位**：上述路由；repository 的 `saveDocs()`、`saveCorpusChanges()`；`app.js` 的 `flushAutomaticModuleSaves()`。
- **处理方向**：先明确联合请求的成功契约，再选择单事务保存或拆成两个独立请求；响应和前端状态必须能表达实际结果。

### A05：普通编辑没有版本条件，多窗口旧草稿会覆盖新修改

- **现状**：普通词条 PUT 不比较客户端的编辑基准版本，直接写入完整词条并生成新的 `updatedAt`。
- **影响**：两个窗口从同一版本开始编辑，后保存的旧草稿会静默覆盖先保存的修改。SQLite 事务只保证单次写入完整，不能识别草稿是否过期。
- **证据级别**：普通 PUT 和 `saveEntry()` 都已确认没有条件更新。“新建来源并绑定”的专用路径有 `expectedUpdatedAt`，但不保护普通编辑，不能视为已解决。
- **定位**：`lib/api-routes.js` 的普通 entries PUT（约 411 行）；repository 的 `saveEntry()`（约 2707 行）。
- **处理方向**：先做目标词条级的 `updatedAt` 条件和明确的冲突反馈，模块保存随后按模块处理；短期不引入词典级 revision。

## 2. 本地 HTTP 与文件访问边界

以下风险都以请求能到达服务为前提。只在本机打开 localhost，不代表服务只监听本机；局域网是否可达还取决于防火墙。显式绑定回环地址能收窄攻击面，但不能替代请求来源和静态资源边界。A06–A08 作为同一项 HTTP 安全边界工作处理。

### A06：没有限制监听地址，API 没有访问边界

- **现状**：`server.js` 使用 `.listen(port)`（约 64 行），日志虽然打印 localhost，代码并未指定回环地址；API 可以读取、导出、修改和删除数据，没有任何访问校验。
- **影响**：能连到端口的其他进程或设备可以调用这些操作。不能仅凭代码断言已暴露到公网。
- **处理方向**：默认显式监听本机，再结合 Host 校验和写请求来源校验，建立适合本地工具的边界。账号、登录和复杂权限体系不是修复的前提。

### A07：静态服务公开整个仓库，路径保护可被绕过

- **现状**：静态根目录就是仓库。越界判断用字符串前缀，私有目录靠区分大小写地匹配 `/data/` 片段来阻止，没有公开资源清单（`lib/static-server.js` 的 `createStaticFileServer()`，约 16–28 行）。
- **影响**：
  - 源码、内部文档和 `.git` 文件都可被请求；
  - Windows 下改变大小写，或使用同前缀的兄弟目录路径，可以绕过限制。
  - 数据目录在默认位置（仓库内的 `data/`）时，私有词库也可能泄露；用 `CONLEXICON_DATA_DIR` 把数据放在仓库外时，只暴露源码和 `.git`。
- **证据**：此前临时文件测试中，`/data/probe.json` 返回 403，`/DATA/probe.json` 返回 200；编码路径可读同前缀兄弟目录；`/.git/config` 可读。未证明可以读取电脑上的任意文件。
- **处理方向**：只公开真正的前端资源（独立 public 目录或明确的资源清单），并用正确的目录包含判断与解码处理。符号链接／junction 及其他平台的利用范围仍需验证。

### A08：写请求不限制跨站来源和媒体类型

- **现状**：服务不校验 Origin；`readRequestBody()`（`lib/http-utils.js` 约 19 行）不要求 JSON 媒体类型，正文能解析为 JSON 就继续执行。
- **证据**：此前带外站 Origin、`Content-Type: text/plain` 的隔离请求成功创建了临时词典。
- **影响与限制**：外站网页可能借此触发修改；真实浏览器攻击还受本地网络访问等限制。没有完成恶意网页的端到端验证，不能把服务端复现等同于所有浏览器都可被攻击。
- **兼容性**：退出时的 beacon 保存已用 `application/json` 类型的 Blob 发送，fetch 兜底也设置了该类型（`app.js` 约 16633–16643 行）。因此“写请求必须是 JSON 媒体类型且来自同源”与现有调用方兼容，不需要额外改造前端。
- **处理方向**：统一限定写请求的来源和媒体类型，beacon 保存走同一边界。

## 3. 规则执行与算法

### A10：IPA 前后文条件：语义缺陷、静默降级与执行时间失控

`lib/ipa-model.js` 的 `conditionMatches()`（约 160 行）把用户写的前后文条件直接当作原生正则执行，同一模型在前端和后端都会运行。四个问题出在同一处，必须一起决定，不能分开修：

1. **锚点只约束一个分支**：前文拼成 `${condition}$`，后文拼成 `^${condition}`。含 `|` 的合法条件里只有一个分支受锚点约束：前文 `ac` 配条件 `a|b`、后文 `cb` 配条件 `a|b` 都被判为匹配（已实测）。用了“或”的规则会在错误位置生效，影响自动 IPA 结果。
2. **无效正则静默降级**：语法错误的条件（如 `[`）会被接受，并退回按字面匹配开头或结尾；保存时也不校验。规则含义在用户不知情时被改变。
3. **执行时间失控（ReDoS）**：此前用嵌套重复条件配约 30 个重复字符做隔离测试，1.5 秒内未结束，由测试超时终止。这不是常规规则的典型耗时，但恶意导入或意外复杂的规则都可能卡住页面或 Node 服务。
4. **每次调用重新编译**：批量生成时开销明显。

- **归属**：2026-10-01 决定由交接文档路线图第 3 阶段“音系与形态规则引擎”（IPA 模块重写）处理，旧模块不再扩展功能；开工前可选先给锚点加非捕获分组止血，需用户确认。
- **处理顺序**：
  1. 先决定规则能力：继续支持完整正则并加可终止的执行边界，还是改为受限的条件语法。捕获语法错误、复用编译结果都解决不了第 3 点；只用于排队、没有超时终止的 Worker 也不算解决。
  2. 再按选定方案一起修锚点分组、错误提示（保存时和沙盒中）以及编译复用。
- 先单独修第 1、2 点再改语法，会让用户规则迁移两次。
- 改动会改变已有规则的生成结果，需在 CHANGELOG 说明；如果改为受限语法，还需要设计已有规则的转换或提示。

### A11：质量检查的循环检测会在无环图上指数级重复展开

- **现状**：`sourceCycleForEntry()` 只记录当前递归路径，节点访问完成后从已访问集合中删除，已查过的无环部分不会被复用。报告又逐词条调用，共享来源会被反复展开。
- **证据**：此前合成无环图实测，45 个词条约 1.8 秒，49 个约 14.3 秒；当前算法未变，浏览器内的具体耗时未实测。
- **影响**：少量但结构特殊的数据就能让同步质量检查明显卡住，不只是“词典很大才慢”。
- **定位**：`lib/quality-model.js` 的 `sourceCycleForEntry()`（约 163 行）及 `buildQualityReport()` 中的逐词条调用；`app.js` 的 `buildQualityViewReport()`。
- **处理方向**：在 F5-1 中复用 `lib/etymology-graph-model.js` 的强连通分量结果，见[质量计划](QUALITY_RESULT_PLAN.md) 4.3 节和[词源图计划](ETYMOLOGY_GRAPH_PLAN.md)第 6 节。见证路径语义按词源图计划第 7 节决策 2 处理。F5 目前只有计划，不代表本项已修复。

## 4. 无关的全量工作

### A12：后端只读接口和保存操作读取无关的大模块

- **现状**：`baseDictionarySnapshot()`（约 2969 行）会解析全部模块并加载形态模板，很多调用方实际只用到其中一部分。GPT 用临时数据复现：关系查询和 facets 每次各自解析约 100 万字符的语料 JSON。实际界面延迟未测。
- **范围修正**：当前 base snapshot 的 `entries` 是空数组，旧报告里的 `normalizeDictionaryWithEntityPlaceholders()` 已不适用，不要再写成“保存 docs 会扫描全库词条和义项 ID”。
- **处理方向**：由[数据规范化计划](DATA_NORMALIZATION_REPAIR_PLAN.md)处理，尚未实装：
  - 阶段 1：只读接口按需读取；
  - 阶段 4：取消普通保存的跨类型 ID 扫描，保存路径随之按需读取。

### A13：前端收到局部保存响应后仍规范化整本已加载词典

- **现状**：`applyDictionaryModulePayload()`（`app.js` 约 16218 行）合并单个模块后调用 `replaceLoadedDictionarySource()`（约 16183 行），后者对整本词典重新执行 `normalizeDictionary()`，包括 entries、corpus 和 morphology。
- **影响**：保存一个小模块，CPU 和对象分配却与整本已加载词典的规模相关；实际界面耗时待测。
- **处理方向**：在模块边界规范化并局部更新状态，保留正确的 summary、缓存失效和草稿语义。数据规范化计划明确不改完整快照维护，该计划完成不等于本项解决；与 A14 一并考虑。

### A14：前端完整词典快照的剩余消费者

2026-09-29 检查，代码变化后需复核。是否移除快照，应先实测 10k／30k 词典下快照的加载耗时、体积和内存再决定：

- **服务端已有能力的本地后备，可以直接删除**：`filteredEntries()` 的本地筛选路径、`refreshActiveFilterState()` 按快照清理失效 ID。
- **整词典批处理，宜改为服务端批处理命令**：`batchGenerateIpa()`、`applyTagSortOrder()`、前端 `buildQualityReport()`（其缓存键 `qualityReportCacheKey()` 本身就要序列化全部词条，为 O(N)）。质量部分即 F5。
- **快照同步维护，快照移除后自然消失**：`upsertEntryInDictionary()`、`removeEntryFromDictionary()`、`applyEntryPatchPayload()`，以及 A13 的整本规范化。

## 5. 代码质量与清理

### C01：前后端规范化函数重复，settings 被反复规范化

- **现状**：`app.js` 复制了 `lib/dictionary-model.js` 26 个函数中的 22 个，已出现字段漂移（前端多出 `toolNavOrder`）。前端有 33 处调用 `normalizeDictionarySettings()` 重复规范化已规范化的 settings，部分位于逐标签的热路径。
- **处理方向**：数据规范化计划阶段 2（共享纯数据规则）和阶段 3（settings 读取收敛）。

### C02：SQLite JSON 读取吞错

- **现状**：`parseJson()` 解析失败时静默返回默认值；settings 损坏时可能被当作空配置，之后随保存写回默认值。
- **处理方向**：数据规范化计划阶段 1。

### C06：数据分析的 8 个加载函数复制粘贴

- **现状**：`loadAnalysisOrthography`、`loadAnalysisTags`、`loadAnalysisRootFamilies`、`loadAnalysisActivity` 等 8 个函数（约 `app.js` 9885–10600 行，状态变量约 216–275 行）流程相同。差异包括请求端点（5 个用 `/analysis/query`，3 个用 `/analysis/features/query`）、请求体、缓存键和“当前是否可见”的判断。
- **处理方向**：单独一次重构，把上述差异全部参数化；每个加载函数保留各自的状态与过期响应检查。以浏览器回归数据分析各页为验收，不以减少行数为目标。

### C07：死代码

- 约 25 个界面文案键只在中英文字典中定义，如 `linkedSource`、`unlinkedSource`、`tableSize`、`morphologyNone`、`glbSmallCaps`、`planned`、`corpusRequiredUnitContent`、`orthographyStressModule`。这是按字面搜索的结果，删前逐个排除动态拼接。
- 无调用方的薄包装可以删除：`search-normalization-model` 的 `DEFAULT_CONFIGURED_SEARCH_NORMALIZATION`、`createSearchNormalizer`，以及 `tag-model` 的 `entryListDisplayTag`。
- 只有测试调用的导出逐个看用途，不批量删除：
  - `sampleSurface` 用于验证生成贴图与解析采样一致，`qualityIssueIdentity` 对应质量计划中的问题身份契约，两者都保留；
  - `fieldFuzzyEnabled`、`normalizeConfiguredSearchText`、`resolveDisplayIdentity`、`findDerivedEntries` 待确认；
  - 删除函数时不能顺带丢掉它们覆盖的行为验证。

### C08：质量模型中永远不会执行的后备路径

- **现状**：`lib/quality-model.js` 对必然加载的 `entryRelationsModel` 使用可选调用，并保留一条依赖缺失时才走的 `find` 后备路径（约 149–160、165、208 行）。
- **处理方向**：F5-1 搬迁质量规则时一并删除。

### C09：数据库非空列与静态 DOM 的读取兜底

- **现状**：对 `NOT NULL` 列的读取仍层层兜底，如 `rowCount || 1` 会把 0 静默改为 1；`elements.xxx?.` 用于静态 DOM，会掩盖 ID 改名错误。
- **限制**：`NOT NULL` 不保证数值大于零，直接删除 `|| 1` 可能把异常尺寸送进渲染。数值完整性另定边界；可选链按节点生命周期逐处判断，留待相关 DOM 工作时处理，不批量删除。
- **审查范围说明**：2026-09-30 复查是按模式扫描后逐处核实，不是逐行审查。`app.js` 中 69 处 `String(x || "")` 和液态玻璃引擎的能力检测没有逐个检查。
