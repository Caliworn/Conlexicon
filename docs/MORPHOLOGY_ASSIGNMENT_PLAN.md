# 形态分配重做计划：表格直接匹配、槽位与 elsewhere

设计日期：2026-10-24。状态：设计草案，已完成独立复评（第 8 节），未实施；第 10 节的决定点须用户确认后才能开工。完成后把仍然有效的契约迁入 `docs/API_CONTRACT.md` 和 [SQLite 后端规范](SQLITE_BACKEND_SPEC.md)，本文删除。

与 [Sense Tag Plan](SENSE_TAG_PLAN.md) 的分工：本计划决定"一组标签上下文会得到哪些形态表"；义项标签计划只负责提供上下文（每个义项一个上下文：词条标签 ∪ 该义项标签）。两者之间唯一的契约见 3.4。

## 1. 背景与目标

现行的形态分配有三个问题（2026-10-23 至 24 与用户讨论确定）：

1. **匹配条件太弱**：模板组的 `matchTags` 只要求"任一标签相同"，无法表达"且"和"非"。
2. **只取最前**：每个词条只能得到一个组。变化表常常是叠加出来的，例如形容词 = 名词性变化 + 级变化；只取最前，就只能把名词性表格复制进一个"形容词组"。
3. **特殊优先靠排序隐式实现**：比如把"不规则名词"组排在"名词"组前面。规则的含义要依赖一个看不见的顺序。

目标：

1. **去掉形态组**：表格成为直接匹配词条的单位，每张表自带匹配规则。
2. **每张表属于一个槽位**：新建表时自动建一个只含它的槽位。同一槽位里的表互相竞争，按 **elsewhere condition** 由更具体的规则胜出；不同槽位之间全部生效，自动组合。这对应形态学理论中 Paradigm Function Morphology 的"规则块"。
3. **只有一套顺序**：槽位顺序就是显示顺序；槽位内表的顺序只在平局时决定先后。顺序不影响哪些表生效。
4. **可视化编辑**：槽位面板展示竞争与具体程度关系，试算面板解释每个槽位为什么选中某张表，影响范围显示规则对整本词典的作用。
5. **现有数据转换后，形态结果完全不变。**

**不做的事**

- 不改单元格的规则语言（`applyMorphologyRuleSyntax()`、`leftV / rightV` 函数），那属于第 3 阶段规则引擎。
- 匹配条件只看标签，不看词形或读音；以后由规则引擎扩展。
- 不做文本形式的匹配表达式（理由见 8.2）。
- 不做与匹配无关的显示分节；显示结构就是槽位结构。

## 2. 当前事实

以下内容都对照了基准提交 `6cf0a5c` 的代码。

**模板数据**（`lib/morphology-model.js`）

- 形态模块是 `{ functions: { leftV, rightV }, templateGroups: [...] }`。
- 组：`{ id, name, matchTags, notes, tables: [...], createdAt, updatedAt }`。
- 表：`{ id, title, rowCount, columnCount, rowLabels, columnLabels, cells: { "r,c": { sourceText } }, createdAt, updatedAt }`，只属于一个组。
- SQLite：`morphology_template_groups(id, position, name, match_tags_json, notes, …)`、`morphology_template_tables(id, group_id, position, title, row_count, column_count, row_labels_json, column_labels_json, …)`、`morphology_template_cells(table_id, row_index, column_index, source_text)`。

**词条数据**

- `morphologyMode` 为 `auto` 或 `manual`；`morphologyGroups: [{ templateGroupId, title, notes, overrides: { [tableId]: { "r,c": value } } }]`。
- **自动模式**：`morphologyGroups` 只是叠加层（标题、备注、覆写），挂在自动解析出的组上。没有内容的叠加层会被丢弃；解析不到的组，其叠加层作为"休眠叠加层"保留，`materializeAutomaticMorphologyGroups()` 切换到手动模式时会把它们一起带过去。
- **手动模式**：`morphologyGroups` 是用户显式选择的有序组列表。
- SQLite：`entry_morphology_groups` 主键 `(entry_id, template_group_id)`，存 `title / notes`；`entry_morphology_cell_overrides` 主键 `(entry_id, template_group_id, template_table_id, row_index, column_index)`，外键指向 `entry_morphology_groups`。

**解析与派生**

- `resolveAutomaticTemplateGroups()`：词条标签与组 `matchTags` 有任一相同即匹配，只取排序最前的组。repository 的 `automaticMorphologyGroupId()` 和旧版本迁移里各有一份相同规则。
- `morphologySearchValueRecords()` 按"组 → 表 → 单元格"生成形态搜索记录；`entry_morphology_search_values` 主键含 `template_group_id`。
- `lib/morphology-write-plan.js`：按组判断生成是否变化（`generationGroupIds`）；`assignmentChanged()` 比较组顺序和各组 `matchTags` 的结构化集合；表被移到别的组、表格缩小或删除组和表时，需要检查词条引用，有引用就返回 409 `morphology_references_in_use`。
- `lib/morphology-analysis-feature.js` 与 `morphologyAnalysis` feature result：summary 的 `groups[]` 给出每个组的 `assignedEntryCount`，`overrideGroups[]`、`overrideTables[]` 统计覆写；筛选 category 支持 `group + templateGroupId` 等；items 的 feature 带 `assignedGroupIds`。

**界面**（`app.js`）

- 详情 `renderMorphologyDisplay()` 按组分节：标题取词条组标题、模板组名，组备注显示在标题下；表标题为空时用组标题。
- 编辑器 `renderMorphologyEntryControls()`：自动 / 手动切换，手动模式可添加、排序、移除组；每组可填词条级标题和备注，每张表有覆写输入格。
- 模板页 `createMorphologyGroupEditor()`：按组编辑名称、`matchTags`、备注，组内编辑表的标题、行列和单元格规则。没有试算或影响范围显示。

## 3. 新模型

### 3.1 模板

```js
morphology: {
  functions: { leftV, rightV },          // 不变
  slots: [{                              // 有序：槽位顺序 = 显示顺序
    id, name, notes,
    tables: [{                           // 有序：只在平局时决定先后
      id, title, notes,
      matchRules: [{ all: [...], none: [...] }],
      rowCount, columnCount, rowLabels, columnLabels, cells,
      createdAt, updatedAt,
    }],
    createdAt, updatedAt,
  }],
}
```

- 每张表恰好属于一个槽位。新建表时自动建一个只含它的槽位，名称默认为空；把表移进另一个槽位，就和那个槽位里的表形成竞争。
- 界面在槽位变空时自动删除它，所以正常编辑不会产生空槽位；外部输入（HTTP、导入）中的空槽位在边界校验中拒绝（3.2）。
- 槽位名称可以为空。只含一张表时，界面不显示槽位名；有两张以上时显示槽位名，空名显示为"未命名槽位"。
- 表新增 `notes`，承接原来组的模板备注（转换见 6.1）。

数据形状上，槽位与旧的组都是"装着有序表格的容器"，但含义相反：组里的表一起生效，槽位里的表互相竞争。界面与说明文字必须写清这一点（见 5.1、8.3）。

### 3.2 匹配规则

每张表的 `matchRules` 是析取范式：

- 行内 `all` 的标签上下文必须全部带有（"且"）；
- 带有 `none` 中任一标签，这一行就不成立（排除）；
- 行与行之间是"或"；
- `matchRules` 为空的表不会自动匹配。

比较时用结构化键（`normalizeStructuralKey`），与现行规则相同。

**校验**（只在外部边界做：形态模块的 `PUT` 和 JSON 导入）

- `all`、`none` 按标签列表规范化；
- `all` 不能为空：只有排除条件的行会匹配几乎所有词条，包括没有标签的词条；
- 同一标签不能同时出现在一行的 `all` 和 `none` 中：这一行会永远不成立；
- 违反时返回 400 `invalid_morphology_match_rule`，`details` 指出表 ID 和行号；
- 槽位里没有表时返回 400 `invalid_morphology_slot`。界面不会产生这种请求，见 3.1。

### 3.3 具体程度与 elsewhere

把一行看成一组条件：`all` 中每个标签是"有它"，`none` 中每个标签是"没有它"。

- **A 行比 B 行更具体**：A 的条件集合真包含 B 的条件集合。这时满足 A 的上下文一定满足 B，反之不然。
- 每一行都只是用"且"连起来的条件，所以集合包含就是逻辑蕴含的精确判断，不需要推理引擎；校验已经排除了自相矛盾的行。

**对一个上下文 S 的解析**：

1. 找出所有表中在 S 上成立的行；
2. 每个槽位内，去掉"比同槽位另一条成立的行更不具体"的行（elsewhere）；
3. 剩下的行所属的表全部生效。

性质：

- 只含一张表的槽位不存在竞争：满足规则就生效。简单词典完全不用关心槽位。
- 同一槽位里两行条件完全相同，或者互不包含时，谁也不覆盖谁，两张表都生效（平局），按槽位内顺序排列。所以把"名词格变化""名词数变化"放进同一槽位、写同样的规则，它们会一起生效；一张规则更具体的"不规则名词变化"表会把它们一起覆盖掉。
- 一张表有多行时，只看实际成立的那几行；只要其中一行没被覆盖，这张表就生效。

### 3.4 与义项标签计划的契约

```js
resolveAutomaticTables(contexts, morphology)  // → 有序的表 ID 列表
explainAutomaticTables(contexts, morphology)  // → 每个上下文、每个槽位的判定过程
```

- `contexts` 是标签集合的列表。词条有多个上下文时，各上下文的结果合并去重；顺序先按槽位，再按槽位内的表顺序。
- `explainAutomaticTables()` 返回每张表的状态和原因，例如"生效"、"被 X 覆盖"、"不满足：缺少 adj"、"不满足：带有排除标签 专名"。试算面板（5.2）使用它，解析契约测试也可以直接断言这些原因。`resolveAutomaticTables()` 的结果必须与它给出的生效表一致。
- 义项标签实施之前，每个词条只有一个上下文：词条标签。义项标签计划落地后，上下文按该计划生成，这两个函数不变。
- repository 的 `automaticMorphologyGroupId()` 删除，所有调用方（模板保存后计算受影响词条、形态分析输入、搜索投影、前端预览与试算）都通过共享函数解析。

### 3.5 词条数据

```js
morphologyMode: "auto" | "manual",
morphologyTables: [{ tableId, notes, overrides: { "r,c": value } }],
```

- 覆写按"词条 + 表 + 单元格"记录。同一张表无论因为哪个上下文生效，都只有一份覆写。
- **自动模式**：`morphologyTables` 只是叠加层（备注、覆写），挂在解析出的表上；没有内容的叠加层丢弃，解析不到的表的叠加层作为休眠叠加层保留。与现行语义相同，只是单位从组变成表。显示顺序跟随模板的槽位顺序。
- **手动模式**：`morphologyTables` 是用户显式选择的有序表列表，显示顺序就是这个列表的顺序。
- 词条级的"组标题"不再存在（转换见 6.2 与决定点 D1）。

### 3.6 SQLite

```sql
CREATE TABLE IF NOT EXISTS morphology_slots (
  id TEXT PRIMARY KEY,
  position INTEGER NOT NULL,             -- 显示顺序
  name TEXT NOT NULL DEFAULT '',
  notes TEXT NOT NULL DEFAULT '',
  created_at TEXT,
  updated_at TEXT
);

-- morphology_template_tables：删除 group_id；新增
--   slot_id TEXT NOT NULL REFERENCES morphology_slots(id),
--   match_rules_json TEXT NOT NULL,
--   notes TEXT NOT NULL DEFAULT ''；
-- position 改为槽位内顺序。

CREATE TABLE IF NOT EXISTS entry_morphology_tables (
  entry_id TEXT NOT NULL REFERENCES entries(id) ON DELETE CASCADE,
  template_table_id TEXT NOT NULL,
  position INTEGER NOT NULL,             -- 只在手动模式下有意义
  notes TEXT NOT NULL DEFAULT '',
  created_at TEXT,
  updated_at TEXT,
  PRIMARY KEY(entry_id, template_table_id)
);

-- entry_morphology_cell_overrides：主键改为
--   (entry_id, template_table_id, row_index, column_index)，
-- 外键指向 entry_morphology_tables(entry_id, template_table_id)。
-- entry_morphology_search_values：删除 template_group_id，主键改为
--   (entry_id, template_table_id, row_index, column_index)。
-- 删除 morphology_template_groups 与 entry_morphology_groups。
```

- `match_rules_json` 是低频配置，按项目原则存 JSON，不拆表。
- 这是 schema 变更，旧数据库须经 JSON 重新导入（2026-10-23 用户确定的开发期规则）。

## 4. 派生与写入

- **搜索投影**：`morphologySearchValueRecords()` 改为按"生效的表 → 单元格"生成，`sourceType: "morphology"`、`sourceId: <tableId>` 不变。
- **写入计划**（`morphology-write-plan.js`）：
  - **生成变化**按表判断（`generationTableIds`）：单元格规则、行列结构，或所用函数变化。
  - **分配变化**：任一表的 `matchRules` 变化、表在槽位之间移动、表的增删。比较规则时用规范形式：每行的 `all`、`none` 各自转成排序后的结构化键集合，行与行之间再整体排序。只改行顺序、行内标签顺序或大小写，不算变化。
  - **只改顺序**（槽位顺序、槽位内顺序）不影响哪些表生效，不触发形态投影重建。搜索投影的 `sourcePosition` 按显示顺序编号，所以需要重写顺序字段，但不重新生成单元格值。
  - 删除表、缩小表格时，如果有词条引用（手动选择、叠加层或越界的覆写），仍返回 409 `morphology_references_in_use`，`details` 改为列出表 ID。"表被移到别的组"这一情况不复存在；表在槽位之间移动不改变覆写的归属，不需要引用检查。
- **形态分析**（`morphologyAnalysis` feature result）：
  - summary 的 `groups[]` 改为 `tables[]`：`{ tableId, slotId, title, assignedEntryCount }`；
  - `overrideGroups[]` 删除，覆写统计只保留 `overrideTables[]`（去掉其中的 `groupId`、`groupName`）；
  - 筛选 category 的 `group + templateGroupId` 改为 `table + templateTableId`，`overrideGroup` 删除；
  - items 的 `assignedGroupIds` 改为 `assignedTableIds`。
  - 这些形状变化同步写入 API 契约。影响范围（5.3）的"当前词条数"直接使用 `tables[].assignedEntryCount`。
- **分配预览端点**（5.3 的"保存前影响"，阶段 3 实施）：
  - `POST /api/dictionaries/:id/morphology/assignment-preview`，请求体是草稿形态模块（形状与 `PUT /morphology` 相同，并做同样的边界校验）；
  - 服务端读取自动模式词条的上下文，分别用当前模板和草稿解析一次，返回 `{ changedEntryCount, gainedByTable: [{ tableId, entryCount }], lostByTable: [{ tableId, entryCount }], sampleEntries: [{ entryId, lemma, gainedTableIds, lostTableIds }] }`；
  - `sampleEntries` 最多 20 条，不返回完整 ID 列表；只读，不写入任何数据。

## 5. 界面

模板页分成三个区域：**槽位面板**（分配：哪些表、什么条件、怎么竞争）、**表格编辑**（内容：行列标签与单元格规则）、**试算面板**（解释）。现有模板页的未保存检查和"保存 / 放弃更改 / 取消"确认流程覆盖整个页面，包括规则、槽位结构和表格内容。

### 5.1 槽位面板

- 槽位按显示顺序纵向排列。每个槽位可以拖拽排序，也有"上移 / 下移"按钮，供键盘使用。
- **只含一张表的槽位**显示为一张普通的表卡片：标题、规则芯片（如 `n, 不规则`、`排除：专名`）、当前词条数（5.3）。
- **含两张以上表的槽位**显示为带标题的容器：
  - 显示槽位名，可就地改名、写备注；
  - 显示说明"同一槽位内只采用最具体的表"；
  - 槽位内用缩进加"覆盖"标记显示具体程度关系，例如"不规则名词变化 覆盖 名词变化"。规则互不包含的表并排显示，标为"可同时生效"。这些关系完全由规则计算得出，不能手工编辑。
- **建立和解除竞争**：把表拖进另一个槽位，或者用表卡片菜单里的"移到槽位…"（键盘可用）。从多表槽位里"移出为独立槽位"时，新槽位紧跟在原槽位后面。
- **规则编辑**：点开表卡片后，规则以行的形式编辑。每行有"同时包含"和"排除"两个逗号分隔的输入框，行与行之间显示"或"；两个框都为空的行在提交前去掉。
- 新建表时自动建一个独立槽位，放在当前选中槽位之后；没有选中的槽位时放在最后。

### 5.2 试算面板

试算面板是让 elsewhere 变得透明的关键。

- **输入**：直接输入一组标签；或者选择一个现有词条，按义项标签计划生成多个上下文（义项标签实施之前，只有词条标签一个上下文）。
- **输出**：调用 `explainAutomaticTables()`，在槽位面板上标出结果：
  - 胜出的表高亮；
  - 被淘汰的表淡化，并写明原因，例如"被'不规则名词变化'覆盖"、"不满足：缺少 adj"、"不满足：带有排除标签 专名"；
  - 多个上下文时按上下文分别显示，并给出合并后的最终表列表。
- 试算使用页面上**未保存的草稿规则**，编辑规则时结果即时更新，不发请求。
- 试算面板与槽位面板并排；窄屏（768px 以下）时试算面板折叠到槽位面板上方，可以展开。

### 5.3 影响范围

- **当前词条数**：每张表卡片显示当前有多少词条用到它，数据来自 `morphologyAnalysis` summary 的 `tables[].assignedEntryCount`。点击数字跳转到这些词条，使用 `table + templateTableId` 筛选。页面有未保存修改时，数字标注"基于已保存的规则"。
- **保存前影响**（阶段 3）：有未保存的分配变化时，页面显示"这次改动会让 N 个词条的变化表发生变化"，并按表列出增加和减少的词条数，以及最多 20 个示例词条。数据来自 4 节的分配预览端点。请求在编辑停止后防抖发出，并且只在存在分配变化时发出：只改顺序或表格内容不发。
- 保存操作不被预览阻塞；预览失败时显示可重试的错误，不影响保存。

### 5.4 表格编辑

- 点开表后，在抽屉（窄屏）或面板右侧区域（宽屏）编辑标题、备注、行列数、行列标签和单元格规则，与槽位面板分开。
- 单元格规则的写法和校验不变（`applyMorphologyRuleSyntax()`、引用语法校验）。

### 5.5 词条侧

- **详情**：按槽位顺序显示生效的表；同一槽位里平局的表按槽位内顺序相邻显示。表标题下显示词条级的表备注。
- **编辑器**：自动 / 手动切换保留。
  - 自动模式下按同样的顺序列出生效的表，每张表可填词条级备注和覆写。
  - 手动模式改为添加、排序、移除表，显示顺序就是手动列表的顺序。
  - 从自动切换到手动时，按当前显示顺序把生效的表和休眠叠加层一起带过去，与现行 `materializeAutomaticMorphologyGroups()` 的语义相同。
- **分析页**：形态分析的分组统计改为按表，按槽位顺序排列。

## 6. 转换（旧 JSON 导入）

转换集中在 `lib/legacy-dictionary-migration.js`；核心规范化模块只处理新形状。更早的 `morphology.tables[]` 形状已有迁移路径，先转成旧组形状，再走同一个转换。

### 6.1 模板：结果完全不变

旧规则是"组按顺序排列，任一标签命中，只取最前"。设旧组依次为 G1…Gn，Gi 的标签集合为 Ti。

- **规则**：Gi 的每张表获得同一组规则。Ti 中每个标签 t 各成一行，`all: [t]`，`none` 为排在前面的所有组的标签之并 T1 ∪ … ∪ Ti-1。
  - 如果 t 已经出现在前面的组里，这一行在旧规则下永远轮不到，直接丢掉；
  - 如果 Gi 的行全部被丢掉，规则为空，这张表不会自动匹配。旧规则下它同样永远不会生效。
- **槽位**：每张旧表各成一个独立槽位，槽位顺序 = 先按旧组顺序，再按组内顺序。生成的规则保证不同旧组不会同时成立，同一旧组的表规则相同、一起生效，所以每个词条生效的表格集合与转换前相同，显示顺序也相同。
- **旧组名**：表标题为空时用组名补上；不为空时，在表备注开头写入组名，例如"原形态组：名词"。
- **旧组的模板备注**：写入该组第一张表的 `notes`，与组名分行。

生成的排除列表可能较长。转换只负责结果不变，之后用户可以借助试算面板，改用槽位和具体程度来简化。

### 6.2 词条

- **覆写**：旧 `overrides[tableId]` 原样转为该表的覆写。旧模型里一张表只属于一个组，所以不会冲突。
- **手动模式**：所选组按顺序展开为它们的表。
- **自动模式叠加层**：按表拆开。旧组的词条级备注写入该组第一张表的叠加层备注；词条级组标题按决定点 D1 处理。
- **休眠叠加层**：同样按表拆开保留。

## 8. 独立复评

按 `AGENTS.md`，把第 3–6 节当作外部提案重新检查。

### 8.1 结论

采用"表格直接匹配 + 每张表属于一个槽位 + 槽位内 elsewhere"，界面以槽位面板、试算面板和影响范围为中心。

- **必要性**：形容词 = 名词性变化 + 级变化这样的组合，在现行模型下只能复制表格；特殊优先只能靠隐式顺序。这两点都是用户实际遇到的问题。
- **为什么是这个方案**：
  - 组合是默认行为，竞争要显式声明（放进同一槽位），具体程度自动决定胜负，不依赖顺序；
  - 只有一套顺序：槽位顺序就是显示顺序，槽位内顺序只处理平局；
  - 只含一张表的槽位就是一张普通的表，简单词典无须了解槽位；
  - 覆写天然按表记录，不存在同一张表的两份覆写；
  - 数据结构是一对多（槽位 → 表），没有多对多关系，也没有可空外键；
  - 和 Paradigm Function Morphology 的规则块对应，以后规则引擎也有现成的理论框架可依。
- **为什么要可视化编辑**：elsewhere 的结果由规则自动计算，不看试算很难判断一张表为什么没生效。试算面板和具体程度关系图把隐式的计算显式化；影响范围让用户在保存前就知道改动会波及多少词条。

### 8.2 已排除的替代方案（记录被采用方案取代的理由）

- **保留组，只取最前**（现状加上结构化规则）：组合仍要复制表格。
- **保留组，所有满足规则的组都生效，二选一靠排除条件**：改动最小，但二选一必须手写排除，漏写就会多出变化表；转换要生成排除列表，而且这种排除会永久成为维护负担。
- **保留组，组引用独立的表，组之间按 elsewhere 比较**：能复用表格，但需要"组 ↔ 表"的多对多关系，而且组必须写成完整的变化表。本方案用"槽位 + 相同规则"就能起到组的打包作用，少一层实体。
- **去掉组，所有表之间统一按 elsewhere 比较，不设槽位**：会误伤组合关系。"不规则形容词名词性变化" `{adj, 不规则}` 比"级" `{adj}` 更具体，会把级表也覆盖掉，而它们根本不是竞争关系。
- **槽位可选，表另有全局顺序**（本计划的初稿）：同时存在"表的全局顺序"和"槽位列表顺序"两套顺序，前者决定显示，后者只用于管理，容易混淆；"无槽位"还是一个需要单独处理的特例。改为每张表都属于一个槽位，槽位顺序就是显示顺序。
- **槽位用自由文本标签，而不是实体**：省一张表，但改名要逐张表修改，拼写不一致时会悄悄拆成两个槽位，也无法承载显示顺序。
- **文本表达式**，如 `(n | adj) & !专名`：需要解析器和转义规则，会和第 3 阶段的规则语法重复；嵌套的"或"也让具体程度无法用集合包含判断。
- **具体程度关系可手工编辑**（例如手动指定"A 覆盖 B"）：会让"规则"与"覆盖关系"两个来源互相矛盾。覆盖关系只从规则计算，界面只负责展示。

### 8.3 风险

- **槽位容易被误认为旧的组**：两者都是"装着表格的容器"，含义却相反。缓解：只含一张表的槽位不显示为容器；多表槽位固定显示"同一槽位内只采用最具体的表"；转换后不建多表槽位，用户第一次接触多表槽位是自己主动拖进去的。
- **"带排除的行更具体"可能出乎意料**：同一槽位里，`{n, 非专名}` 比 `{n}` 更具体；上下文没有"专名"时，前者会覆盖后者。这符合 elsewhere 的定义，试算面板会写明覆盖原因。只在同一槽位内发生。
- **同一槽位内的平局会让两张表都生效**：如果用户本意是二选一，会看到两张表，试算面板会标为"可同时生效"。不做静态冲突检测（见决定点 D2）。
- **失去组标题**：依赖组名作为显示标题的词典，转换后标题落在表上（6.1）。
- **改动面大**：模板、词条、分析、搜索投影、写入计划，以及模板页、词条编辑器、详情三处界面都要改，模板页还是整体重做。要靠转换契约和"转换前后每个词条的解析结果逐一相同"的测试兜底，界面分阶段落地。
- **分配预览的成本**：每次预览要对所有自动模式词条解析两次。解析只做集合运算、不生成单元格，压力词典上需要实测；超出可接受范围时，可以只在用户点击"计算影响"时发请求，不自动防抖。

### 8.4 验收

- `node scripts/check-all.js`。
- **解析契约**，覆盖以下情况：
  - 行内"且"、行间"或"、排除；
  - 单表槽位满足即生效、不同槽位叠加；
  - 槽位内更具体者胜出；
  - 槽位内条件相同或互不包含时都生效；
  - 多上下文合并去重；
  - 显示顺序只由槽位顺序和槽位内顺序决定；
  - 空规则不匹配；
  - 各条校验错误；
  - `explainAutomaticTables()` 的原因与 `resolveAutomaticTables()` 的结果一致。
- **转换契约**：用 `scripts/generate-morphology-test-dictionary.js`、`scripts/generate-stress-dictionary.js` 生成的词典按旧模型解析一遍，转换后再解析一遍，每个词条生效的表格集合、显示顺序与单元格值逐一相同；覆写、手动选择、休眠叠加层都保留。
- **写入计划契约**：只改顺序不触发分配变化和单元格重新生成；改规则或在槽位之间移动表，只重建受影响词条的投影；删除被引用的表返回 409。
- **分配预览契约**：草稿与当前模板相同时 `changedEntryCount` 为 0；增减计数与逐个词条比较的结果一致；不写入任何数据。
- **性能**：在压力词典上对比改动前后的模板保存、形态投影全量重建和形态分析耗时，并测量分配预览的耗时。
- **界面**：按 `AGENTS.md` 的 UI 验收清单（中英文、明暗主题、三套皮肤、长标题与长标签、320／480／768／1024／1440px、键盘与 tooltip 层级）。另外检查：
  - 每个拖拽操作都能用按钮或菜单完成；
  - 试算结果随草稿规则即时更新；
  - 模板页与词条形态编辑的离开确认流程正常。

## 10. 待用户确认的决定点

**已确定（用户）**

- 现行的"任一标签相同即匹配"必须改，不用子集或超集判断；改用可以自定义"且 / 或"的结构化规则，不做文本表达式（2026-10-23）。
- 去掉形态组，表格直接匹配词条并自动组合；需要竞争的表放进槽位，槽位内按 elsewhere 由更具体者胜出（2026-10-24）。
- 编辑界面以槽位面板、试算面板和影响范围为中心（2026-10-24）。
- 每张表属于一个槽位，新建表时自动建一个独立槽位；槽位顺序就是显示顺序，槽位内顺序只决定平局时的先后。槽位因此必须是实体（原 D3）。
- 显示结构就是槽位结构，不另设显示分节（原 D4）。

**待用户确认**

- **D1**：词条级的"组标题"转换后怎么处理？建议：非空时写入该组第一张表叠加层备注的开头，例如"原标题：……"，保证数据不丢；以后不再提供词条级标题。另一种做法是直接丢弃。
- **D2**：同一槽位内出现平局（条件相同或互不包含）时，两张表都生效并在试算面板标为"可同时生效"（建议），还是在模板页对潜在冲突做静态提示？静态提示需要分析所有可能的上下文，成本较高。
- **D5**："保存前影响"是在编辑停止后自动防抖请求（建议，前提是压力词典实测可以接受），还是只在用户点击"计算影响"时请求？

**待用户确认：代理拟定的设计选择**（正文已按这些方案书写，确认或修改后再定稿）

- **M1 排除条件**：每行可以写排除标签（`none`）。
- **M2 禁止只有排除的行**：`all` 不能为空；同一标签不能同时出现在一行的 `all` 和 `none` 中。
- **M3 带排除的行算更具体**：同一槽位里，`{n, 非专名}` 比 `{n}` 更具体，会覆盖后者。这是 elsewhere 定义的直接推论，但会影响用户写规则的方式。
- **M4 覆盖关系只由规则计算**：界面只展示，不能手工指定"A 覆盖 B"。
- **M5 匹配只看标签**：不看词形、读音等其他属性，以后由规则引擎扩展。
- **M6 词条级备注按表**：每张生效的表可以写一条词条级备注，不再有按组的标题和备注。
- **M7 手动模式改为选表**：手动列表的顺序就是显示顺序；从自动切到手动时，带上生效的表和休眠叠加层（沿用现行语义）。
- **M8 槽位的显示**：只含一张表的槽位不显示槽位名；多表槽位的空名显示为"未命名槽位"；槽位在界面上变空时自动删除。
- **M9 新建与移出的位置**：新建表的独立槽位放在当前选中槽位之后，没有选中的槽位时放在最后；"移出为独立槽位"时新槽位紧跟原槽位。
- **M10 转换去向**：旧组名补进空的表标题，或者写进表备注开头；旧组的模板备注写进该组第一张表的备注；旧组的词条级备注写进该组第一张表的词条级备注（词条级组标题见 D1）。
- **M11 试算面板**：使用未保存的草稿规则，即时更新；窄屏（768px 以下）折叠到槽位面板上方。
- **M12 表格内容编辑的位置**：窄屏在抽屉里，宽屏在面板右侧区域，与槽位面板分开。
- **M13 影响范围的细节**：有未保存修改时，当前词条数标注"基于已保存的规则"；保存前影响最多给 20 个示例词条；预览失败不阻塞保存。
