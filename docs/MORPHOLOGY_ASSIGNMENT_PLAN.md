# 形态分配重做计划：表格直接匹配、槽位与 elsewhere

设计日期：2026-10-24，2026-11-21 定稿。状态：设计定稿，未实施。完成后把仍然有效的契约迁入 `docs/API_CONTRACT.md` 和 [SQLite 后端规范](SQLITE_BACKEND_SPEC.md)，本文删除。

与释义标签（[Definition Tag Specification](DEFINITION_TAG_SPEC.md)）的分工：释义标签规范定义词条标签、释义标签和有效标签；本计划决定形态匹配用哪些标签集合（2.4），以及这些集合会得到哪些形态表（2.3、2.5）。

## 1. 问题

### 1.1 现行模型的问题

1. **匹配条件太弱**：模板组的 `matchTags` 只要求"任一标签相同"，无法表达"且"和"非"。
2. **只取最前**：每个词条只能得到一个组。变化表常常是叠加出来的，例如形容词 = 名词性变化 + 级变化；只取最前，就只能把名词性表格复制进一个"形容词组"。
3. **特殊优先靠排序隐式实现**：比如把"不规则名词"组排在"名词"组前面。规则的含义要依赖一个看不见的顺序。
4. **不规则子类只能复制整张表**：一个子类只在几格上不同，也要把整张表抄一遍，之后改原表时副本不会跟着变。逐词覆写只解决单个词，解决不了一整类词。
5. **格按位置寻址，行列只能在末尾增减**：在中间插一行，要把下面每一行的规则手动往下挪，逐词覆写也得跟着挪。
6. **合形只能抄规则**：几格系统性同形时，要把同一条规则写进每一格，改一处要改几处，逐词覆写也不会传递。
7. **分不清"不存在"和"没填"**：空格同时表示这两种意思；逐词覆写也不能表示某个词缺某一格。

### 1.2 现状

以下内容对照基准提交 `6cf0a5c`；格的寻址、尺寸调整和搜索投影的字段对照 `ed01367`。

**模板数据**（`lib/morphology-model.js`）

- 形态模块是 `{ functions: { leftV, rightV }, templateGroups: [...] }`。
- 组：`{ id, name, matchTags, notes, tables: [...], createdAt, updatedAt }`。
- 表：`{ id, title, rowCount, columnCount, rowLabels, columnLabels, cells: { "r,c": { sourceText } }, createdAt, updatedAt }`，只属于一个组。`sourceText` 去掉首尾空白后为空，就当作空格。
- SQLite：`morphology_template_groups(id, position, name, match_tags_json, notes, …)`、`morphology_template_tables(id, group_id, position, title, row_count, column_count, row_labels_json, column_labels_json, …)`、`morphology_template_cells(table_id, row_index, column_index, source_text)`。

**词条数据**

- `morphologyMode` 为 `auto` 或 `manual`；`morphologyGroups: [{ templateGroupId, title, notes, overrides: { [tableId]: { "r,c": value } } }]`。覆写值是字面字符串，空值在规范化时丢掉（`normalizeMorphologyOverrides()`）。
- **自动模式**：`morphologyGroups` 只是叠加层（标题、备注、覆写），挂在自动解析出的组上。没有内容的叠加层会被丢弃；解析不到的组，其叠加层作为"休眠叠加层"保留，`materializeAutomaticMorphologyGroups()` 切换到手动模式时会把它们一起带过去。
- **手动模式**：`morphologyGroups` 是用户显式选择的有序组列表。
- SQLite：`entry_morphology_groups` 主键 `(entry_id, template_group_id)`，存 `title / notes`；`entry_morphology_cell_overrides` 主键 `(entry_id, template_group_id, template_table_id, row_index, column_index)`，外键指向 `entry_morphology_groups`。

**解析与派生**

- `resolveAutomaticTemplateGroups()`：有效标签与组 `matchTags` 有任一相同即匹配，只取排序最前的组。repository 的 `automaticMorphologyGroupId()` 和旧版本迁移里各有一份相同规则。
- `morphologySearchValueRecords()` 按"组 → 表 → 单元格"生成形态搜索记录，字段是值、组 ID、表 ID、行列下标和 `sourcePosition`，不含行列标签；`entry_morphology_search_values` 主键含 `template_group_id`。
- `lib/morphology-write-plan.js`：按组判断生成是否变化（`generationGroupIds`）；`assignmentChanged()` 比较组顺序和各组 `matchTags` 的结构化集合；表被移到别的组、表格缩小或删除组和表时，需要检查词条引用，有引用就返回 409 `morphology_references_in_use`。
- `lib/morphology-analysis-feature.js` 与 `morphologyAnalysis` feature result：summary 的 `groups[]` 给出每个组的 `assignedEntryCount`，`overrideGroups[]`、`overrideTables[]` 统计覆写；筛选 category 支持 `group + templateGroupId` 等；items 的 feature 带 `assignedGroupIds`。

**界面**（`app.js`）

- 详情 `renderMorphologyDisplay()` 按组分节：标题取词条组标题、模板组名，组备注显示在标题下；表标题为空时用组标题。空格显示为空白单元格。
- 编辑器 `renderMorphologyEntryControls()`：自动 / 手动切换，手动模式可添加、排序、移除组；每组可填词条级标题和备注，每张表有覆写输入格。
- 模板页 `createMorphologyGroupEditor()`：按组编辑名称、`matchTags`、备注，组内编辑表的标题、行列标签和单元格规则。尺寸用"行数""列数"两个数字框加"应用尺寸"按钮调整，只能在末尾增减；行列标签为空时填成序号。没有试算或影响范围显示。

### 1.3 目标

1. **去掉形态组**：表格成为直接匹配词条的单位，每张表自带匹配规则。
2. **每张表属于一个槽位**：同一槽位里的表互相竞争，按 **elsewhere condition** 由更具体的规则胜出；不同槽位之间全部生效，自动组合。这对应 Paradigm Function Morphology 的"规则块"。
3. **只有一套顺序**：槽位顺序就是显示顺序；槽位内表的顺序只在平局时决定先后。顺序不影响哪些表生效。
4. **按释义匹配**：每条释义各自匹配，结果不同时详情分栏显示。
5. **表可以显式继承另一张表**：子表只写不同的格，其余格沿用父表。
6. **格有明确的状态**：规则、不存在、同某格（合形）、还没填；逐词覆写也能标"不存在"。
7. **行列有稳定 ID**：可以在任意位置插入、删除、调整顺序，格、覆写和引用不受影响。
8. **可视化编辑**：槽位面板展示竞争与具体程度关系，试算面板解释每个槽位为什么选中某张表，影响范围显示规则对整本词典的作用。
9. **现有数据转换后，形态结果完全不变。**

### 1.4 不做的事

- 不改单元格的规则语言（`applyMorphologyRuleSyntax()`、`leftV / rightV` 函数），那属于第 3 阶段规则引擎。
- 匹配条件只看标签，不看词形或读音；以后由规则引擎扩展。
- 不做文本形式的匹配表达式（理由见第 3 节）。
- 不做与匹配无关的显示分节；显示结构就是槽位结构。
- 不做跨表的格引用，也不做"取某格作词干再加后缀"，这些归规则引擎。
- 不做多维特征空间；多级表头记在交接文档的路线图（见第 4 节）。
- 模板页和词条编辑器不合并显示合形的格，只有详情合并（2.14）。

## 2. 方案

### 2.1 模板数据

```js
morphology: {
  functions: { leftV, rightV },          // 不变
  slots: [{                              // 有序：槽位顺序 = 显示顺序
    id, name, notes,
    tables: [{                           // 有序：只在平局时决定先后
      id, title, notes,
      matchRules: [{ all: [...], none: [...] }],   // 2.2
      inheritsFrom,                      // 父表 ID 或 null（2.8）
      rows: [{ id, label }],             // 有序；子表不带，沿用链顶表（2.6）
      columns: [{ id, label }],
      cells: [Cell],                     // 2.7
      createdAt, updatedAt,
    }],
    createdAt, updatedAt,
  }],
}
```

- 每张表恰好属于一个槽位。新建表时自动建一个只含它的槽位，名称默认为空；把表移进另一个槽位，就和那个槽位里的表形成竞争。
- 界面在槽位变空时自动删除它，所以正常编辑不会产生空槽位；外部输入（HTTP、导入）中的空槽位在边界校验中拒绝（2.2）。
- 槽位名称可以为空。只含一张表时，界面不显示槽位名；有两张以上时显示槽位名，空名显示为"未命名槽位"。
- 表新增 `notes`，承接原来组的模板备注（转换见 2.15）。

数据形状上，槽位与旧的组都是"装着有序表格的容器"，但含义相反：组里的表一起生效，槽位里的表互相竞争。界面与说明文字必须写清这一点（2.13）。

### 2.2 匹配规则

每张表的 `matchRules` 是析取范式：

- 行内 `all` 的标签上下文必须全部带有（"且"）；
- 带有 `none` 中任一标签，这一行就不成立（排除）；
- 行与行之间是"或"；
- `matchRules` 为空的表不会自动匹配。

比较时用结构化键（`normalizeStructuralKey`），与现行规则相同。

**校验**（只在外部边界做：形态模块的 `PUT` 和 JSON 导入）

- `all`、`none` 按标签列表规范化；
- `all` 不能为空：只有排除条件的行会匹配几乎所有词条，包括没有标签的词条；
- 同一标签不能同时出现在一行的 `all` 和 `none` 中：这一行会永远不成立；
- 违反时返回 400 `invalid_morphology_match_rule`，`details` 指出表 ID 和行号；
- 槽位里没有表时返回 400 `invalid_morphology_slot`。

### 2.3 具体程度与 elsewhere

把一行看成一组条件：`all` 中每个标签是"有它"，`none` 中每个标签是"没有它"。

- **A 行比 B 行更具体**：A 的条件集合真包含 B 的条件集合。这时满足 A 的上下文一定满足 B，反之不然。
- 每一行都只是用"且"连起来的条件，所以集合包含就是逻辑蕴含的精确判断，不需要推理引擎；校验已经排除了自相矛盾的行。
- 排除条件也算条件：同一槽位里，"`n`，排除 `专名`"比 `n` 更具体，上下文不带"专名"时前者覆盖后者。

**对一个上下文 S 的解析**：

1. 找出所有表中在 S 上成立的行；
2. 每个槽位内，去掉"比同槽位另一条成立的行更不具体"的行（elsewhere）；
3. 剩下的行所属的表全部生效。

性质：

- 只含一张表的槽位不存在竞争：满足规则就生效。简单词典完全不用关心槽位。
- **平局**：同一槽位里两行条件完全相同，或者互不包含时，谁也不覆盖谁，两张表都生效，按槽位内顺序排列，试算面板标为"可同时生效"。不做静态冲突检测。所以把"名词格变化""名词数变化"放进同一槽位、写同样的规则，它们会一起生效；一张规则更具体的"不规则名词变化"表会把它们一起覆盖掉。
- 一张表有多行时，只看实际成立的那几行；只要其中一行没被覆盖，这张表就生效。

### 2.4 匹配上下文：按释义

- 每条释义一个上下文：词条标签 ∪ 该释义标签。没有标签的释义，上下文就是词条标签。词条没有释义时，只有一个上下文：词条标签。
- 词条标签参与每个上下文，因为变化类这样的词级标签通常挂在词条上。这只是匹配输入，不改变"释义不继承词条标签"的显示与筛选语义。
- **使用约定**：变化类、不规则这类词级属性标在词条上。标在某一条释义上时，其他释义的上下文里没有它，可能匹配到通用表；详情会把这种差异分栏显示（2.14），用户能直接看到。
- 各上下文的结果合并去重，得到词条的生效表。覆写、搜索投影、形态分析和分配预览都使用合并后的结果；只有详情和词条编辑器的标注按上下文区分。
- 释义都没有标签时，结果等于只用词条标签，现有数据不受影响。

例：释义 1 标 `n, 古语`，释义 2 标 `v`，表规则为 `v, 古语`。没有任何一条释义同时带 v 和古语，所以这张表不生效。释义 1 标 `n`，释义 2 标 `专名`，名词表规则为 `n`、排除 `专名`：释义 1 的上下文是 `{n}`，名词表生效。

### 2.5 解析契约

```js
morphologyMatchContexts(entry)                // → [{ definitionId, tags }]；没有释义时 definitionId 为 null
resolveAutomaticTables(contexts, morphology)  // → { tableIds, contexts: [{ definitionId, tableIds }] }
explainAutomaticTables(contexts, morphology)  // → 每个上下文、每个槽位的判定过程
```

- 三个函数都在共享模型里，所有调用方（模板保存后计算受影响词条、形态分析、搜索投影、分配预览、前端详情、编辑器与试算）都通过它们解析。repository 的 `automaticMorphologyGroupId()` 和前端的旧匹配实现删除。
- `tableIds` 是合并去重后的结果，顺序先按槽位，再按槽位内的表顺序；`contexts[].tableIds` 是每个上下文各自的结果，顺序规则相同。
- `explainAutomaticTables()` 返回每张表的状态和原因，例如"生效"、"被 X 覆盖"、"不满足：缺少 adj"、"不满足：带有排除标签 专名"、"可同时生效"。`resolveAutomaticTables()` 的结果必须与它给出的生效表一致。

### 2.6 行与列

- 非子表有有序的 `rows` 和 `columns`，各至少一项；每项是 `{ id, label }`，ID 由程序按"前缀 + UUID"生成（`mrow-`、`mcol-`）。
- 格、逐词覆写、合形引用都按 `(rowId, columnId)` 定位。子表的格使用链顶表的行列 ID。
- 显示顺序就是列表顺序。标签可以为空，空标签显示为该行（列）的序号。
- **格名**：搜索结果、试算、确认弹窗、合形标注等需要说"这一格叫什么"的地方，统一通过 `morphologyCellLabel(table, rowId, columnId)` 生成，现在是"行标签·列标签"。

**操作**

- 插入：在上方／下方插入行，在左侧／右侧插入列；表格末尾的边上各有"+ 行""+ 列"。
- 调整顺序：上移／下移行，左移／右移列。
- 删除行或列。只剩一行（列）时，删除不可用。
- 这些操作都在行表头、列表头的菜单里，键盘可用。子表的表头菜单不可用，并提示"形状由父表 X 决定"。

**删除行列的后果**

- 模板里这一行（列）的格在草稿里立刻删掉，链上所有子表在这一行（列）上的格一并删掉。保存前可以用"放弃更改"撤回。
- 指向被删格的"同某格"变回还没填。
- 被删的行列上如果有逐词覆写（包括子表上的覆写），保存时先确认再删除，见 2.12。

插入和调整顺序不改动格、覆写和引用；调整顺序只改变显示顺序和合并区域（2.14）。

### 2.7 格的状态与解析

**存储的状态**

| 层级 | 没有记录 | 规则 | 字面形式 | 不存在 | 同某格 |
|---|---|---|---|---|---|
| 普通表（链顶表）的格 | 还没填 | ✓ | — | ✓ | ✓ |
| 子表的格 | 沿用父表 | ✓ | — | ✓ | ✓ |
| 逐词覆写 | 跟随模板 | — | ✓ | ✓ | — |

- 模板里存的是规则，按 lemma 计算出形式；逐词覆写存的是字面形式。
- 规则文本去掉首尾空白后为空，规范化时丢掉，等于没有记录。
- 子表不能显式标"还没填"；逐词覆写不能设"同某格"。

```js
// 模板格：tables[].cells
{ rowId, columnId, kind: "rule", sourceText }
{ rowId, columnId, kind: "absent" }
{ rowId, columnId, kind: "refer", targetRowId, targetColumnId }

// 逐词覆写：morphologyTables[].overrides
{ rowId, columnId, kind: "form", value }
{ rowId, columnId, kind: "absent" }
```

**解析一格**

1. 看这个词在这张表这一格上有没有覆写：写了形式就用这个形式；标了不存在，结果就是不存在。
2. 没有覆写，就从当前表开始沿继承链往上，取第一条记录：
   - 规则：按 lemma 计算；
   - 不存在：结果就是不存在；
   - 同某格：回到第 1 步解析目标格，所以目标格上的覆写和继承都会生效；
   - 到链顶都没有记录：还没填。

**显示结果**

- **形式**：非空字符串，正常显示。
- **空白**：还没填，或者规则计算出空字符串（条件分支没有命中、也没写 else）。详情显示空白。
- **不存在**：详情显示"—"。

解析结果同时带上"是否经由同某格得到、最终来源格是哪一格"，详情用它计算合并区域，编辑器用它显示"= 格名"。只有"形式"生成搜索值。

**校验**（形态模块的 `PUT` 与 JSON 导入）

- 每张表里同一个 `(rowId, columnId)` 最多一条记录；坐标必须落在表（子表为链顶表）的形状之内；字段必须与 `kind` 相符。
- 违反时返回 400 `invalid_morphology_cell`，`details` 指出表 ID、格和原因。引用相关的校验见 2.9。

### 2.8 表继承

用于不规则子类：子类只在少数几格上与某张表不同。子表显式指定父表，只写不同的格。

**语义**

- `inheritsFrom` 指向同一形态模块里的另一张表，不要求在同一槽位。父表的父表也照样生效，形成一条继承链；允许多层，不设层数上限。
- **形状沿用链顶表**：子表的行列和行列标签都取自链顶表，不能单独修改。链顶表增删、调整行列，子表随之变化；新插入的行列在子表里都是"沿用父表"。
- 子表的格可以没有记录（沿用父表），也可以写规则、标不存在或设同某格，覆盖父表。解析顺序见 2.7。
- **继承只决定内容，不参与分配**：
  - 子表有自己的匹配规则、槽位、标题和备注，这些都不从父表继承；
  - 父表是否对当前词条生效、在不在同一槽位，都不影响子表的内容；
  - 通常把子表放进父表的槽位，用更具体的规则覆盖父表。例如父表"名词二变"的规则是 `{n, 二变}`，子表"二变不规则"是 `{n, 二变, 不规则}`。
- 词条覆写照常按"词条 + 子表 + 格"记录，继承来的格也可以覆写。

**改换父表与解除继承**

- 改换父表只能换成同一链顶下的另一张表（形状相同），且不能形成循环。要换到另一个链顶下的表，先解除继承。
- **解除继承**：这张表成为新的链顶表。
  - 复制链顶表当时的行列，生成新的行列 ID；
  - 原来沿用父表的格，复制沿链解析出的那条记录（同某格的目标换成新 ID）；
  - 这张表自己的格、这张表上的逐词覆写，以及它所有后代表的格和逐词覆写，都换到新的行列 ID 上。
- **删除被继承的父表**：返回 409 `morphology_table_has_children`，`details` 列出子表 ID；界面提示先解除这些子表的继承。

**边界校验**

- `inheritsFrom` 必须指向同一模块里存在的表，链上不能有循环；
- 子表不能带 `rows`、`columns`；
- 违反时返回 400 `invalid_morphology_inheritance`，`details` 指出表 ID 和原因。

**不处理的跨变化类不规则**

例如俄语的重音类型与变格类交叉，同一种移重音模式出现在不同的变格类里；又如在任何变化里都缺同样几格的缺项词。这类不规则是在底表产出的形式上再做一层操作，而不是另填一套成品形式，归第 3 阶段规则引擎（格内条件、作用于其他槽位输出的操作层，见第 4 节）。在那之前，缺项词可以用逐词覆写的"不存在"处理。

### 2.9 合形

系统性合形（拉丁语中性名词主格 = 宾格、俄语动物性阳性名词宾格 = 属格）用"同某格"状态表示；偶然同形不标记。

- "同某格"指向同一张表（子表为链顶表的形状）里的另一格，有方向：编辑来源格，指向它的格跟着变。
- **引用在最后一步解析**：先叠好逐词覆写和继承，再按引用取值（2.7）。因此：
  - 某个词的属格不规则，覆写属格，宾格自动跟着变；
  - 动物性宾格不需要条件引用：子表"阳性动物名词"继承"阳性名词"，只把宾格设为"同属格"；
  - 将来分析或搜索可以区分系统性合形和偶然同形。
- 词条在引用格上写了自己的形式，就是只对这个词断开引用；清空后恢复跟随。
- 允许链式引用（A 同 B，B 同 C）。目标是"不存在"时，结果也是"不存在"；目标还没填时，结果是空白。

**校验**

- 目标必须落在形状之内，不能指向自己；
- **循环按每张表叠好继承后的完整格局检查**：父表里 A 同 B、B 写了规则，父表本身没问题；子表把 B 设为同 A，叠上继承后 A 同 B，就成了环。逐词覆写不能产生引用，所以不会引入新的环；
- 违反时返回 400 `invalid_morphology_cell`。

### 2.10 词条数据

```js
morphologyMode: "auto" | "manual",
morphologyTables: [{ tableId, notes, overrides: [Override] }],   // Override 见 2.7
```

- 覆写按"词条 + 表 + 格"记录。同一张表无论因为哪个上下文生效，都只有一份覆写。
- **自动模式**：`morphologyTables` 只是叠加层（备注、覆写），挂在解析出的表上；没有内容的叠加层丢弃，解析不到的表的叠加层作为休眠叠加层保留。与现行语义相同，只是单位从组变成表。显示顺序跟随模板的槽位顺序。
- **手动模式**：`morphologyTables` 是用户显式选择的有序表列表，显示顺序就是这个列表的顺序。
- 每张表可以写一条词条级备注；词条级的组标题不再存在（转换见 2.15）。
- 校验：覆写坐标必须落在表的形状之内，同一格最多一条，字段与 `kind` 相符；违反时返回 400 `invalid_morphology_override`。

```sql
CREATE TABLE IF NOT EXISTS morphology_template_tables (

-- 只有链顶表有行列
CREATE TABLE IF NOT EXISTS morphology_template_rows (

  position INTEGER NOT NULL,
  label TEXT NOT NULL DEFAULT ''

CREATE TABLE IF NOT EXISTS morphology_template_columns (

CREATE TABLE IF NOT EXISTS morphology_template_cells (

  column_id TEXT NOT NULL REFERENCES morphology_template_columns(id) ON DELETE CASCADE,
  kind TEXT NOT NULL CHECK (kind IN ('rule', 'absent', 'refer')),
  source_text TEXT,
  target_row_id TEXT REFERENCES morphology_template_rows(id),
  target_column_id TEXT REFERENCES morphology_template_columns(id),
  PRIMARY KEY (table_id, row_id, column_id),
  CHECK (
    (kind = 'rule'   AND source_text <> '' AND target_row_id IS NULL AND target_column_id IS NULL) OR
    (kind = 'absent' AND source_text IS NULL AND target_row_id IS NULL AND target_column_id IS NULL) OR
    (kind = 'refer'  AND source_text IS NULL AND target_row_id IS NOT NULL AND target_column_id IS NOT NULL)
  )
);

CREATE TABLE IF NOT EXISTS entry_morphology_tables (
  entry_id TEXT NOT NULL REFERENCES entries(id) ON DELETE CASCADE,
  template_table_id TEXT NOT NULL,
  position INTEGER NOT NULL,             -- 只在手动模式下有意义
  notes TEXT NOT NULL DEFAULT '',
  created_at TEXT,
  updated_at TEXT,

);

CREATE TABLE IF NOT EXISTS entry_morphology_cell_overrides (
  entry_id TEXT NOT NULL,
  template_table_id TEXT NOT NULL,
  row_id TEXT NOT NULL REFERENCES morphology_template_rows(id) ON DELETE CASCADE,
  column_id TEXT NOT NULL REFERENCES morphology_template_columns(id) ON DELETE CASCADE,
  kind TEXT NOT NULL CHECK (kind IN ('form', 'absent')),
  value TEXT,
  PRIMARY KEY (entry_id, template_table_id, row_id, column_id),
  FOREIGN KEY (entry_id, template_table_id)
    REFERENCES entry_morphology_tables(entry_id, template_table_id) ON DELETE CASCADE,
  CHECK ((kind = 'form' AND value <> '') OR (kind = 'absent' AND value IS NULL))

-- entry_morphology_search_values：删除 template_group_id 与行列下标，主键改为
--   (entry_id, template_table_id, row_id, column_id)。
-- 删除 morphology_template_groups 与 entry_morphology_groups。
```

- `match_rules_json` 是低频配置，按项目原则存 JSON，不拆表。
- 删除行列时由外键级联删掉格和覆写；覆写的删除先经过 API 层的确认（2.12）。合形目标的外键不级联，残留的引用会让事务失败，写入前由草稿把这些格改回还没填。
- 子表的格引用的是链顶表的行列，数据库无法约束"同一条链"，由边界校验保证。
- 这是 schema 变更，旧数据库须经 JSON 重新导入。

### 2.12 派生与写入

- **搜索投影**：按合并后的生效表 → 格生成，只为"形式"生成记录；`sourceType: "morphology"`、`sourceId: <tableId>` 不变，`sourcePosition` 按显示顺序编号。
- **写入计划**（`morphology-write-plan.js`）：
  - **生成变化**按表判断（`generationTableIds`）：格的记录、行列的增删，或所用函数变化。一张表的格或行列变了，沿链向下的全部后代也算生成变化；改 `inheritsFrom` 或解除继承时，这张表及其后代都算生成变化。继承关系不算分配变化。
  - **分配变化**：任一表的 `matchRules` 变化、表在槽位之间移动、表的增删。比较规则时用规范形式：每行的 `all`、`none` 各自转成排序后的结构化键集合，行与行之间再整体排序。只改行顺序、行内标签顺序或大小写，不算变化。
  - **只改顺序**（槽位顺序、槽位内顺序、行列顺序）不影响哪些表生效，也不改变格的值，只重写搜索投影的 `sourcePosition`。
  - **行列标签**只影响显示和格名，不触发投影重建。
  - **删除表**：有词条引用（手动选择、叠加层或覆写）时返回 409 `morphology_references_in_use`，`details` 列出表 ID；仍被继承时返回 409 `morphology_table_has_children`（2.8）。表在槽位之间移动不改变覆写的归属，不需要引用检查。
  - **删除行列**：被删的行列上有逐词覆写（包括后代子表上的覆写）时，返回 409 `morphology_override_deletion_unconfirmed`，`details` 是 `[{ tableId, rowId | columnId, label, entryCount }]`。前端弹出独立的确认弹窗，例如"删除'呼格'行会一并删除 12 个词条在这一行上的覆写"，其他表里因此变回还没填的引用格数由前端从草稿算出，一并列出。确认后请求体带 `confirmOverrideDeletion: true` 重新保存，服务端在同一事务里删除。
- **形态分析**（`morphologyAnalysis` feature result）：
  - summary 的 `groups[]` 改为 `tables[]`：`{ tableId, slotId, title, assignedEntryCount }`，按合并后的生效表计数；
  - `overrideGroups[]` 删除，覆写统计只保留 `overrideTables[]`（去掉其中的 `groupId`、`groupName`）；
  - 筛选 category 的 `group + templateGroupId` 改为 `table + templateTableId`，`overrideGroup` 删除；
  - items 的 `assignedGroupIds` 改为 `assignedTableIds`。
  - 这些形状变化同步写入 API 契约。影响范围（2.13）的"当前词条数"直接使用 `tables[].assignedEntryCount`。
- **分配预览端点**（2.13 的"保存前影响"，阶段 3 实施）：
  - `POST /api/dictionaries/:id/morphology/assignment-preview`，请求体是草稿形态模块（形状与 `PUT /morphology` 相同，并做同样的边界校验）；
  - 服务端取自动模式词条的上下文，分别用当前模板和草稿解析一次，比较合并后的生效表，返回 `{ changedEntryCount, gainedByTable: [{ tableId, entryCount }], lostByTable: [{ tableId, entryCount }], sampleEntries: [{ entryId, lemma, gainedTableIds, lostTableIds }] }`；
  - `sampleEntries` 最多 20 条，不返回完整 ID 列表；只读，不写入任何数据。

### 2.13 模板页

模板页分成三个区域：**槽位面板**（分配：哪些表、什么条件、怎么竞争）、**表格编辑**（内容：行列与格）、**试算面板**（解释）。现有模板页的未保存检查和"保存 / 放弃更改 / 取消"确认流程覆盖整个页面，包括规则、槽位结构和表格内容。

**槽位面板**

- 槽位按显示顺序纵向排列。每个槽位可以拖拽排序，也有"上移 / 下移"按钮，供键盘使用。
- **只含一张表的槽位**显示为一张普通的表卡片：标题、规则芯片（如 `n, 不规则`、`排除：专名`）、当前词条数；子表另显示"继承自 X"。
- **含两张以上表的槽位**显示为带标题的容器：
  - 显示槽位名，可就地改名、写备注；
  - 显示说明"同一槽位内只采用最具体的表"；
  - 槽位内用缩进加"覆盖"标记显示具体程度关系，例如"不规则名词变化 覆盖 名词变化"。规则互不包含的表并排显示，标为"可同时生效"。这些关系完全由规则计算得出，不能手工编辑。
- **建立和解除竞争**：把表拖进另一个槽位，或者用表卡片菜单里的"移到槽位…"（键盘可用）。从多表槽位里"移出为独立槽位"时，新槽位紧跟在原槽位后面。
- **规则编辑**：点开表卡片后，规则以行的形式编辑。每行有"同时包含"和"排除"两个逗号分隔的输入框，行与行之间显示"或"；两个框都为空的行在提交前去掉。
- 新建表时自动建一个独立槽位，放在当前选中槽位之后；没有选中的槽位时放在最后。
- 表卡片菜单另有"新建继承此表的子表"（默认放进父表所在槽位、紧跟父表）、"设置父表…"和"解除继承"，键盘可用。

**试算面板**

- **输入**：直接输入一组标签；或者选择一个现有词条，按 2.4 生成上下文。
- **输出**：调用 `explainAutomaticTables()`，在槽位面板上标出结果：
  - 胜出的表高亮；
  - 被淘汰的表淡化，并写明原因，例如"被'不规则名词变化'覆盖"、"不满足：缺少 adj"、"不满足：带有排除标签 专名"；
  - 多个上下文时按释义分别显示，并给出合并后的最终表列表。
- 试算使用页面上**未保存的草稿规则**，编辑规则时结果即时更新，不发请求。
- 试算面板与槽位面板并排；窄屏（768px 以下）时试算面板折叠到槽位面板上方，可以展开。

**影响范围**

- **当前词条数**：每张表卡片显示当前有多少词条用到它。点击数字跳转到这些词条，使用 `table + templateTableId` 筛选。页面有未保存修改时，数字标注"基于已保存的规则"。
- **保存前影响**（阶段 3）：有未保存的分配变化时，页面显示"这次改动会让 N 个词条的变化表发生变化"，并按表列出增加和减少的词条数，以及最多 20 个示例词条。请求在编辑停止后防抖发出，并且只在存在分配变化时发出：只改顺序或表格内容不发。压力词典实测超出可接受范围时，改为只在点击"计算影响"时请求。
- 保存操作不被预览阻塞；预览失败时显示可重试的错误，不影响保存。

**表格编辑**

- 点开表后，在抽屉（窄屏）或面板右侧区域（宽屏）编辑标题、备注、行列和格，与槽位面板分开。
- 行列的插入、移动、删除在表头菜单里（2.6）。
- 每格显示它的状态：
  - 规则：可编辑的规则输入框，写法和校验不变（`applyMorphologyRuleSyntax()`、引用语法校验）；
  - 不存在：单独样式，标"不存在"；
  - 同某格：显示"= 格名"，用次要文字色；
  - 链顶表还没填的格：占位文字"未填写"；
  - 子表没有记录的格：占位文字显示沿链解析出的内容。
- 格的菜单（键盘可用）：标为不存在、设为同…、清除。"设为同…"进入选格模式，点目标格或用方向键加 `Enter` 确认，`Esc` 取消。
- 行表头、列表头菜单另有"整行同…""整列同…"，选一个目标行（列）后逐格设引用，数据仍逐格存储。
- 子表：行列与标签只读，表头菜单不可用。
- 表格编辑不合并显示合形的格。

### 2.14 词条侧

**详情**

- 按槽位顺序显示生效的表，表标题下显示词条级的表备注。
- **按释义分栏**：对每个槽位，取每个上下文在这个槽位里生效的表集合。
  - 所有上下文的集合都相同：通栏显示一次（集合为空就不显示）。
  - 否则，把集合相同的上下文归为一组，每个非空集合占一栏，栏头标"释义 1、3"（编号与详情中的释义编号一致）；集合为空的上下文不占栏。
  - 栏内的表按槽位内顺序排列。宽度不够并排时各栏上下堆叠，栏头保留。
  - 手动模式没有上下文，不分栏。
- **"不存在"**显示"—"，空白显示为空单元格。
- **合形合并**：
  - **区域**：最终来源相同的格（沿同某格的链解析到同一个来源格），加上来源格自身，按上下左右相邻求连通块，对角不算。只看同某格关系：形式碰巧相同不合并；"不存在"和空白格不合并；被逐词覆写断开的格不在区域内。合并区域按叠好继承和逐词覆写之后的结果计算。
  - **渲染**：仍用 `<table>`。在区域内选一个内接矩形，给它的左上格加 `rowspan`／`colspan` 显示形式；区域里其余的格保留为空 `<td>`，放一份视觉隐藏的形式文本供读屏；区域内相邻格之间的边设为 `border-style: hidden`（`border-collapse: collapse` 下优先级最高），只留区域外轮廓。
  - **内接矩形**：枚举完全落在区域里的所有矩形，依次比较：面积最大；矩形中心离区域重心最近；列数更多；最靠上、最靠左。
  - 同一个来源的几个不连通区域各自合并、各自显示形式。

**编辑器**

- 自动 / 手动切换保留。
- 自动模式下按槽位顺序列出合并后的生效表，不是所有释义都生效的表标上"释义 1、3"；每张表可填词条级备注和覆写。
- 覆写格：
  - 没有覆写时，占位文字显示模板算出的结果；
  - 格的菜单可以标为不存在，或清除覆写；
  - 同某格的格旁边显示小标签"= 格名"，占位形式随来源格的覆写实时更新；在这里写形式就是对这个词断开引用，清空后恢复跟随。
- 编辑器不合并显示合形的格。
- 手动模式改为添加、排序、移除表，显示顺序就是手动列表的顺序。
- 从自动切换到手动时，按当前显示顺序把生效的表和休眠叠加层一起带过去，与现行 `materializeAutomaticMorphologyGroups()` 的语义相同。

**分析页**：形态分析的分组统计改为按表，按槽位顺序排列。

### 2.15 转换（旧 JSON 导入）

转换集中在 `lib/legacy-dictionary-migration.js`；核心规范化模块只处理新形状。更早的 `morphology.tables[]` 形状已有迁移路径，先转成旧组形状，再走同一个转换。

**模板：结果完全不变**

旧规则是"组按顺序排列，任一标签命中，只取最前"。设旧组依次为 G1…Gn，Gi 的标签集合为 Ti。

- **规则**：Gi 的每张表获得同一组规则。Ti 中每个标签 t 各成一行，`all: [t]`，`none` 为排在前面的所有组的标签之并 T1 ∪ … ∪ Ti-1。
  - 如果 t 已经出现在前面的组里，这一行在旧规则下永远轮不到，直接丢掉；
  - 如果 Gi 的行全部被丢掉，规则为空，这张表不会自动匹配。旧规则下它同样永远不会生效。
- **槽位**：每张旧表各成一个独立槽位，槽位顺序 = 先按旧组顺序，再按组内顺序。生成的规则保证不同旧组不会同时成立，同一旧组的表规则相同、一起生效，所以每个词条生效的表格集合与转换前相同，显示顺序也相同。
- **行列与格**：按旧的行列数生成行列 ID，行列标签照抄；原来的 `"r,c"` 对应到新的行列 ID。`sourceText` 非空的格转成 `rule`，空格丢掉，即还没填，所以详情显示与转换前相同。
- **旧组名**：表标题为空时用组名补上；不为空时，在表备注开头写入组名，例如"原形态组：名词"。
- **旧组的模板备注**：写入该组第一张表的 `notes`，与组名分行。

生成的排除列表可能较长。转换只负责结果不变，之后用户可以借助试算面板，改用槽位和具体程度来简化。

旧规则只看有效标签；转换后按释义匹配。释义都没有标签时两者相同；释义带标签的词条，结果可能变化，这是 2.4 的预期行为，转换契约按释义都没有标签的词典验证结果不变。

**词条**

- **覆写**：旧 `overrides[tableId]["r,c"]` 转为该表的 `{ kind: "form", value }`，坐标换成行列 ID。旧模型里一张表只属于一个组，所以不会冲突。
- **手动模式**：所选组按顺序展开为它们的表。
- **自动模式叠加层**：按表拆开。旧组的词条级备注写入该组第一张表的叠加层备注；词条级组标题非空时，写在这条备注的开头，例如"原标题：……"。
- **休眠叠加层**：同样按表拆开保留。

## 3. 设计取舍

**为什么是"表格直接匹配 + 槽位 + 槽位内 elsewhere"**

- 组合是默认行为，竞争要显式声明（放进同一槽位），具体程度自动决定胜负，不依赖顺序；
- 只有一套顺序：槽位顺序就是显示顺序，槽位内顺序只处理平局；
- 只含一张表的槽位就是一张普通的表，简单词典无须了解槽位；
- 覆写天然按表记录，不存在同一张表的两份覆写；
- 数据结构是一对多（槽位 → 表），没有多对多关系；
- 和 Paradigm Function Morphology 的规则块对应，以后规则引擎也有现成的理论框架可依。

elsewhere 的结果由规则自动计算，不看试算很难判断一张表为什么没生效，所以编辑界面以试算面板、具体程度关系和影响范围为中心。

**分配方式上排除的做法**

- **保留组，只取最前**（现状加上结构化规则）：组合仍要复制表格。
- **保留组，所有满足规则的组都生效，二选一靠排除条件**：二选一必须手写排除，漏写就会多出变化表；转换要生成排除列表，而且这种排除会永久成为维护负担。
- **保留组，组引用独立的表，组之间按 elsewhere 比较**：需要"组 ↔ 表"的多对多关系，而且组必须写成完整的变化表。"槽位 + 相同规则"就能起到组的打包作用，少一层实体。
- **去掉组，所有表之间统一按 elsewhere 比较，不设槽位**：会误伤组合关系。"不规则形容词名词性变化" `{adj, 不规则}` 比"级" `{adj}` 更具体，会把级表也覆盖掉，而它们根本不是竞争关系。
- **槽位可选，表另有全局顺序**：同时存在两套顺序，容易混淆；"无槽位"还是一个需要单独处理的特例。
- **槽位用自由文本标签，而不是实体**：改名要逐张表修改，拼写不一致时会悄悄拆成两个槽位，也无法承载显示顺序。
- **文本表达式**，如 `(n | adj) & !专名`：需要解析器和转义规则，会和第 3 阶段的规则语法重复；嵌套的"或"也让具体程度无法用集合包含判断。
- **具体程度关系可手工编辑**：会让"规则"与"覆盖关系"两个来源互相矛盾。
- **比较具体程度时不算排除条件**：排除条件就成了只决定成立与否、却不参与竞争的特例，elsewhere 也不再等同于逻辑蕴含。
- **平局时做静态冲突提示**：要分析所有可能的标签组合，成本高；试算面板已经能标出"可同时生效"。

**匹配上下文**

- **只用一个上下文，即有效标签**（词条标签 ∪ 所有释义标签）：更简单，和筛选口径一致，但规则用了"且"或排除、而相关标签分在不同释义上时会出错：释义 1 标 `n, 古语`、释义 2 标 `v` 时误匹配"`v` 且 `古语`"；释义 2 标 `专名` 时名词表被误排除；随释义变化的屈折（hang 的 hung／hanged）只剩更具体的那张表。按释义匹配的代价是要求词级属性标在词条上，分栏显示把这种问题暴露出来。
- **按整组分栏**：同一张表会在几栏里重复出现；按槽位分栏只在真正不同的槽位拆开。

**表继承**

- **空格隐式回退到被覆盖的表**：回退目标取决于胜出关系，而胜出关系取决于词条带哪些标签，同一张不规则表对不同词条可能回退到不同的底表；按平局规则，底表实际上只能有一张，直接指明更清楚。
- **继承也带上分配**（子表继承父表的规则，或父表不生效时子表也不生效）：分配和内容两套机制互相干扰，试算面板也解释不清。
- **子表有自己的形状**：要按标签对齐两张表，父表加行加列时容易错位。需要不同形状的子类就建一张独立的表。
- **复制表格并提供"与原表同步"按钮**：仍然存在两份数据，同步时机还要由人来记。
- **删除父表时把子表转成独立表**：删除这一个动作会悄悄改变别的表；先解除继承再删除，每一步的后果都看得见。

**行列与格**

- **继续按位置寻址，插删时由服务端整体挪位**：保存的是最终状态，服务端分不清"删了第 2 行"和"改了第 2 行以后的内容、再删最后一行"，前端得另外发操作记录；每插一行都要改写这张表上所有词条的覆写；子表和合形引用也得一起挪。
- **多维特征空间，表格只是二维投影**：实际的变化表很少是完整的笛卡尔积（不定式没有人称、复数不分性），会塞满"不存在"或者要处理稀疏组合；入门要先定义维度、再配置排版；维度在整本词典共用还会让模板互相耦合。它的主要收益（按特征写合形、按特征定位一格）要等规则引擎才用得上。二维表加稳定行列 ID 是它的特例，以后可以给行列加特征标注（第 4 节）。
- **普通表不区分"不存在"和"还没填"**：两种意思在详情里看起来一样，"不存在"在三个层级上的含义也不统一。
- **子表能显式标"还没填"、逐词覆写能设"同某格"**：现在没有对应的需求；需要时再加，不影响已有数据。

**合形**

- **继续抄规则**：改一处要改几处，逐词覆写也不会传递。
- **把合并单元格存成数据**：只适用于相邻的格；逐词覆写一断开引用，表的形状就得变。合并只作为显示，从引用推出来。
- **在规则语法里加"取某格的值"**：整格相同是一种状态，不是一段规则文本；真正需要"取某格作词干"时属于规则引擎。
- **只合并正好成矩形的区域**：L 形、T 形的合形同样是一个形式，退回逐格显示反而看不出它们是一组。
- **按形式相同合并**：会把偶然同形也合在一起。

**已知代价**

- **槽位容易被误认为旧的组**：只含一张表的槽位不显示为容器；多表槽位固定显示"同一槽位内只采用最具体的表"；转换后不建多表槽位，用户第一次接触多表槽位是自己主动拖进去的。
- **失去组标题**：依赖组名作为显示标题的词典，转换后标题落在表上。
- **一张子表的完整内容要沿链看才知道**：编辑时没有记录的格显示解析出的内容。
- **改动面大**：模板、词条、分析、搜索投影、写入计划，以及模板页、词条编辑器、详情三处界面都要改，模板页整体重做。靠转换契约和"转换前后每个词条的解析结果逐一相同"的测试兜底，界面分阶段落地。
- **分配预览的成本**：每次预览要对所有自动模式词条按释义解析两次。解析只做集合运算、不生成单元格，在压力词典上实测。

## 6. 验收

- `node scripts/check-all.js`。
- **解析契约**：
  - 行内"且"、行间"或"、排除；
  - 单表槽位满足即生效、不同槽位叠加；
  - 槽位内更具体者胜出，带排除的行更具体；
  - 槽位内条件相同或互不包含时都生效；
  - 按释义生成上下文：没有标签的释义取词条标签，没有释义时只有一个上下文；各上下文结果合并去重；
  - 显示顺序只由槽位顺序和槽位内顺序决定；
  - 空规则不匹配；
  - 各条校验错误；
  - `explainAutomaticTables()` 的原因与 `resolveAutomaticTables()` 的结果一致。
- **格与继承契约**：
  - 2.7 的解析顺序：覆写的形式与不存在、沿链取第一条记录、到链顶还没填；
  - 多层继承；链顶表增删和调整行列时子表随之变化；
  - 同某格在覆写和继承之后解析：覆写来源格时引用格跟着变，覆写引用格时只对这个词断开；链式引用；目标不存在或还没填时的结果；
  - 叠好继承后才出现的引用循环被拒绝；
  - 只有"形式"生成搜索值；父表的格变化时子表的搜索投影随之重建；
  - 解除继承后，这张表及其后代的格、覆写和引用都换到新的行列 ID，解析结果不变；
  - 每条边界校验错误（继承循环、子表带行列、坐标越界、重复的格、字段与 `kind` 不符、引用自身）。
- **行列操作契约**：插入和调整顺序不改变任何格的值；删除行列删掉对应的格，指向它的引用变回还没填；有逐词覆写时未确认返回 409、确认后一并删除；只剩一行（列）时不能删除。
- **转换契约**：用 `scripts/generate-morphology-test-dictionary.js`、`scripts/generate-stress-dictionary.js` 生成的词典（释义都没有标签）按旧模型解析一遍，转换后再解析一遍，每个词条生效的表格集合、显示顺序与单元格值逐一相同；覆写、手动选择、休眠叠加层、词条级组标题都保留。
- **写入计划契约**：只改顺序或行列标签不触发分配变化和单元格重新生成；改规则或在槽位之间移动表，只重建受影响词条的投影；删除被引用的表、仍被继承的父表各返回对应的 409。
- **分配预览契约**：草稿与当前模板相同时 `changedEntryCount` 为 0；增减计数与逐个词条比较的结果一致；不写入任何数据。
- **显示算法**：合并区域与内接矩形的选择（竖列、横行、L 形、T 形、方块加一格、不连通区域、被逐词断开的格）；按释义分栏的分组（全部相同、部分相同、某些上下文为空）。
- **性能**：在压力词典上对比改动前后的模板保存、形态投影全量重建和形态分析耗时，并测量分配预览的耗时。
- **界面**：按 `AGENTS.md` 的 UI 验收，按改动影响选维度。另外检查：
  - 每个拖拽操作都能用按钮或菜单完成，选格模式可以只用键盘完成；
  - 试算结果随草稿规则即时更新；
  - 模板页与词条形态编辑的离开确认流程正常，删除行列的确认弹窗是独立弹窗；
  - 合并区域在每套皮肤、明暗主题下都看得出来：只画行线的皮肤里横向合并可能看不出，必要时给区域加统一的淡底色；
  - 读屏逐格读到合并区域里每一格的形式。

## 7. 决定记录

- 现行的"任一标签相同即匹配"必须改，不用子集或超集判断；改用可以自定义"且 / 或"的结构化规则，不做文本表达式（2026-10-23）。
- 去掉形态组，表格直接匹配词条并自动组合；需要竞争的表放进槽位，槽位内按 elsewhere 由更具体者胜出（2026-10-24）。
- 编辑界面以槽位面板、试算面板和影响范围为中心（2026-10-24）。
- 每张表属于一个槽位，新建表时自动建一个独立槽位；槽位顺序就是显示顺序，槽位内顺序只决定平局时的先后；显示结构就是槽位结构（2026-10-24）。
- 不规则子类用显式表继承，子表的形状沿用父表（2026-11-20）。
- 匹配上下文按释义生成，结果不同时详情按槽位分栏（2026-11-21）。
- "不存在"在普通表、子表和逐词覆写三个层级都支持；普通表区分"不存在"和"还没填"，旧数据的空格按还没填转换（2026-11-21）。
- 合形用"同某格"引用表示，详情把任意连通的区域合并显示，文字放在面积最大的内接矩形里（2026-11-21）。
