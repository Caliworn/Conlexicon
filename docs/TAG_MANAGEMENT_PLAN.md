# 标签管理计划

状态：设计草案，已做独立复评（第 9 节），未实施。第 11 节的决定点 D1–D8 已由用户确认（2026-10-25）；代理拟定的设计选择清单仍待确认。

## 1. 背景与目标

标签相关的配置现在分散在"其他设置"的四个文本框里，随"保存配置"整体提交：词性、排序、显示替换、红色强调。它们各自按不同规则匹配标签，排序只能靠手写列表，筛选菜单里的词性也不跟随排序。

目标：

1. 用一张**有序的标签登记表**取代这四项设置，作为词典标签的唯一配置来源。
2. 登记表分两个区：**词性区**永远排在**普通标签区**之前；放进词性区的标签就是词性。
3. 标签管理页做成独立的导航目的地，**每次改动立即保存**，不进入设置表单的未保存检查和离开确认。"其他设置"中"词条标签"小节的其余显示偏好也全部移到这个页面，设置页不再有标签相关的项。
4. 词条里出现的新标签自动登记到普通区末尾；已登记的标签除非手动删除，否则不会消失；当前没有词条使用的标签显示为灰色。
5. 列表、详情、有效标签、筛选菜单（含词性）、分析页的组合行统一按登记表排序。

不在本计划范围内（可作为后续候选）：改名与合并标签（批量改写词条）、编辑框中的标签自动补全、标签颜色多于红色一种。

## 2. 当前事实（已对照代码确认）

- 四项设置位于 settings 模块（`module_blobs.settings`），由 `lib/dictionary-data-model.js:103-111` 规范化，随设置表单经 `PUT /settings` 保存。该端点是部分更新：服务端把请求体合并进已存设置，IPA 固定保留（`mergeOtherSettings`，`lib/sqlite-dictionary-repository.js:435`）。
- 匹配规则不一致：
  - 词性按结构键（只去首尾空白、区分大小写）匹配，`lib/tag-model.js` 的 `entryParts`；
  - 排序按 `normalizeText`（忽略大小写）匹配，`arrangeTagsByOrder`；
  - 红色强调同时匹配原始标签和显示替换文本，并忽略大小写，`tagIsRedHighlighted`；
  - 显示替换按原始值精确查表，`displayTag`。
- 有效标签（词条标签与全部释义标签的并集）在读取时按 `tagSortOrder` 排序，前后端共用 `tagModel.effectiveEntryTags`；运行期词条写入在服务端按同一顺序存储（`normalizeEntryForSave`，`lib/sqlite-dictionary-repository.js:3312`）；JSON 导入保持原顺序，存量词条由批处理 `applyTagOrder` 整理。
- 设置保存后若 `tagSortOrder` 有变化，前端试运行批处理并询问是否立即整理（`app.js` 的 `offerTagOrderForExistingEntries`）。
- 筛选 facets 的词性按 `localeCompare` 字母序排列（`lib/sqlite-dictionary-repository.js:2434`），不跟随排序；facets 的 `tags` 字段按使用数排序，前端未使用。
- 每个标签的使用词条数已有缓存：`entryTagIdentitySnapshotFromDatabase`（同文件 2007 行），按查询会话 generation 失效。
- 运行期词条的标签行只在 `writeEntryProjection` 写入；JSON 导入走另一处批量写入（同文件约 3963 行）。
- 质量规则只读取 `partOfSpeechTags`（`qualityInputSettings`）；形态模板匹配不读取这四项设置。
- 标签输入框按半角逗号、全角逗号和顿号拆分（`parseTagListText`），所以标签本身不能含这三种字符。
- 标签层级标注与三条标签层级质量规则共用的 `definitionTagLayerStates`（`lib/tag-model.js`，2026-10-25 新增）也读取 `partOfSpeechTags`；实施时须一并改为读取登记表。

## 3. 数据模型

### 3.1 存储

新增关系表（第 9.2 节说明为什么不用 blob）：

```sql
CREATE TABLE tag_registry (
  tag TEXT PRIMARY KEY,                       -- 原始标签值，已去首尾空白
  part_of_speech INTEGER NOT NULL,            -- 1 = 词性区，0 = 普通区
  position INTEGER NOT NULL,                  -- 区内顺序，从 0 连续
  display_label TEXT NOT NULL DEFAULT '',     -- 空 = 显示原始值
  red_highlight INTEGER NOT NULL DEFAULT 0,
  UNIQUE (part_of_speech, position)
);
```

**标签不设代理 ID**：标签值本身就是主键。词条和释义一直按值引用标签（`entry_tags.tag`、`definition_tags.tag`），不需要另一层身份；代理 ID 会要求两张标签表改为按 ID 引用，牵动搜索投影、筛选和导入导出，本计划没有需要它的功能。

`entry_tags.tag` 与 `definition_tags.tag` 增加外键 `REFERENCES tag_registry(tag)`（不级联删除）。这样不变量 1（下一节）和"在用标签不能删除"都由数据库约束保证；两张表已有以 `tag` 开头的索引（`idx_entry_tags_tag_entry`、`idx_definition_tags_tag_entry`），删除登记行时的外键检查不需要全表扫描。写入顺序随之确定：先登记，再写标签行。

`partOfSpeechTags`、`tagSortOrder`、`tagDisplayMap`、`redHighlightTags` 从 settings 中移除。其余八项标签显示偏好不是逐个标签的数据，仍存于 settings，但改由标签管理页编辑，经 `PUT /settings` 保存（第 6.4 节）：

| 字段 | 含义 |
| --- | --- |
| `tagListSeparatorStyle` | 标签输入框重新显示时的分隔符 |
| `entryListRawTagDisplay` | 词条列表的标签行显示原始标签 |
| `entryListRawPartDisplay` | 词条列表的词性文本（副标题和释义前）显示原始标签 |
| `filterMenuRawTagDisplay` | 筛选菜单中显示原始标签 |
| `entryHoverCardRawTagDisplay` | 词条悬浮卡片中显示原始标签（2026-10-25 新增） |
| `entryListTagDisplayLimit` | 词条列表中标签显示上限（2–10，默认 3） |
| `entryListTagsIncludeParts` | 词条列表的标签行包含词性标签 |
| `entryListTagFiltering` | 在词条列表中点击标签时按标签筛选 |

### 3.2 不变量

1. **登记表覆盖全部在用标签**：`entry_tags` 与 `definition_tags` 中出现的每个值都在 `tag_registry` 中。由外键保证，写入路径在同一事务内先登记新值（第 4 节），不靠读取时补齐。
2. **只增不减**：除了在管理页手动删除，任何操作都不删除登记行；删除词条、改写标签后旧标签留在表中，变为灰色。
3. **顺序显式**：每个区内 `position` 唯一且连续。
4. **身份按原始值**：标签身份是去首尾空白后的原始字符串，逐字符比较，不做大小写折叠或 Unicode 规范化，与有效标签、词性筛选和形态匹配一致。`Noun` 与 `noun` 是两行（D7）。

### 3.3 排序规则

标签的排名 = 词性区按 `position`，然后普通区按 `position`。共享模型提供 `tagRank(registry)`，所有显示和保存时排序都用它：

- 有效标签：先按首次出现拼出并集，再按排名稳定排序。
- 尚未登记的标签（只在未保存的草稿、快速录入预览中出现）排在所有已登记标签之后，保持输入顺序。

## 4. 登记规则

| 来源 | 行为 |
| --- | --- |
| 运行期词条写入（新建、保存、`PATCH /entries`、创建或绑定来源时改写的词条、整词典批处理） | `writeEntryProjection` 写标签行之前，把未登记的值 `INSERT` 到普通区末尾。同一次写入里的多个新标签按出现顺序登记：词条标签在前，然后按释义顺序 |
| 快速录入 | 经同一保存端点，规则同上 |
| JSON 导入（当前格式） | 文件中的 `tagRegistry` 原样写入（边界校验），再把文件中在用但未登记的标签按首次出现追加到普通区末尾 |
| JSON 导入（旧格式，无 `tagRegistry`） | 由旧数据转换生成登记表，见第 7.2 节 |
| 管理页手动添加 | 添加到所选区的末尾，使用数为 0，显示为灰色 |

新标签一律进普通区，不会自动成为词性。

## 5. 生效范围

| 位置 | 改动 |
| --- | --- |
| 词条列表、悬浮卡片、衍生词卡片、详情头部与释义标签、词汇网络节点 | 显示前按排名排序（有效标签已经如此，改为读登记表） |
| 保存时排序 | 词条标签和每条释义标签分别按排名存储，使编辑框文字顺序与登记表一致 |
| 筛选菜单与排序菜单的词性胶囊 | facets `parts` 改按登记表顺序 |
| 词性判断（筛选 `part`／`partCount`／`partSet`、统计、多词性分析、质量规则、卡片上的词性分层） | 词性集合 = 词性区的标签 |
| 分析页标签组合与词性组合行 | 组合内的标签按排名排列；行本身仍按词条数排序 |
| 显示替换、红色强调 | 读登记行的 `displayLabel`、`redHighlight`，按原始值精确匹配 |
| 形态模板匹配 | 不变，只看标签值 |

改动顺序后，已有词条只有编辑框里的文字顺序与登记表不同，显示不受影响。

## 6. API

### 6.1 读取

- `GET /api/dictionaries/:id` 增加 `tagRegistry: { tag, partOfSpeech, displayLabel, redHighlight }[]`，按排名排列（数组顺序即顺序，不暴露 `position`）。前端进入状态时建立一次排名索引，替代原先读取四项设置的位置。
- `GET /api/dictionaries/:id/tag-registry` 供管理页使用：`{ id, generation, tags }`，每行在上述字段之外加 `entryCount`（按有效标签计数，0 即灰色）和 `displayAmbiguous`。计数复用标签身份快照。

### 6.2 修改

`POST /api/dictionaries/:id/tag-registry/changes`，请求体是**单个操作**，返回 `{ id, updatedAt, tagRegistry }`（含计数，与读取端点同形）：

| 操作 | 请求体 | 说明 |
| --- | --- | --- |
| 添加 | `{ op: "add", tag, partOfSpeech }` | 加到该区末尾 |
| 移动 | `{ op: "move", tag, partOfSpeech, before }` | `before` 为同区的另一个标签，或 `null` 表示该区末尾；跨区移动即改变是否为词性 |
| 修改 | `{ op: "update", tag, displayLabel?, redHighlight? }` | 只改给出的字段 |
| 删除 | `{ op: "delete", tag }` | 只允许删除没有词条使用的标签 |

用操作而不是整表替换，是为了让多个标签页同时打开时，一边拖动不会抹掉另一边刚登记的新标签。

错误码：`tag_registry_invalid_tag`（空值或含分隔符）、`tag_registry_tag_exists`、`tag_registry_tag_not_found`、`tag_registry_anchor_not_found`（`before` 不在目标区）、`tag_registry_tag_in_use`（删除在用标签，409，`details.entryCount`；服务端在同一事务内先计数再删除，外键是最后一道约束）、`invalid_tag_registry_change`（请求体格式无效）。

每次修改使该词典的查询会话失效（词性集合、显示名和顺序都进入了摘要 DTO、筛选与统计）。

### 6.3 其他端点的变化

- 词条写入类端点：本次写入登记了新标签时，响应额外带 `tagRegistry`（不含计数），前端整体替换状态中的登记表；没有新标签时不带。
- `PUT /settings`、带 settings 的 `PATCH /entries`：不再涉及四项设置。
- 批处理 `applyTagOrder`：保留，顺序来源改为登记表，由标签管理页调用（D4）。

### 6.4 标签显示偏好

不新增端点。标签管理页的"显示"面板每改一项，就以 `PUT /settings` 发送只含该字段的请求体；服务端合并进已存设置，其余设置不受影响。"其他设置"表单删去这八项后不再发送它们，已存的值由同一合并规则保留，不需要额外的保留或忽略规则。前端用响应中的 settings 替换状态，与现有设置保存相同。

代价：`PUT /settings` 每次都会使该词典的查询会话失效，而这八项只影响前端显示，切换一次会让下一次查询重新计算。这些偏好很少修改，接受这一开销，不为它另设端点。

## 7. 导入、导出与旧数据

### 7.1 导出与当前格式导入

导出 JSON 顶层增加 `tagRegistry`（含灰色行），往返保持不变。导入在边界校验：值非空且不含分隔符、无重复、字段类型正确；不合规整次拒绝。

### 7.2 旧格式转换

由 `lib/legacy-dictionary-migration.js` 负责，输入为四项旧设置与词典中实际在用的标签：

1. **词性区**：`partOfSpeechTags` 中的标签。先按在 `tagSortOrder` 中的位置，未列出的按 `partOfSpeechTags` 原顺序排在后面。
2. **普通区**：`tagSortOrder` 中的非词性项按原顺序；其余在用标签按首次出现（词条顺序，词条标签在前、释义标签在后）。
3. **大小写**：旧排序和红色强调忽略大小写。一项旧配置匹配到多个在用值（如 `Noun` 匹配 `noun` 与 `NOUN`）时，这些值共享该位置，按首次出现排列。
4. **红色强调**：旧配置可能写的是显示替换文本，按"原始值或显示文本"解析为原始值。
5. **没有对应在用标签的旧配置**（只出现在词性、排序、显示替换或红色强调里的值）登记为灰色行，保留原有设置，不丢弃。
6. 转换后 settings 中不再保留四项旧字段。

可见变化：原排序把非词性标签排在词性前面的词典，转换后词性会移到最前；这是"词性永远在前"规则的直接结果。

### 7.3 已有 SQLite 词典

已有 SQLite 词典通过导出导入迁移：用实施前的版本导出 JSON，更新后在词典管理中导入，登记表由第 7.2 节的转换生成。不提供转换脚本，也不在启动时自动升级（`AGENTS.md`）。README 的数据存储一节同步写明这一步。

## 8. 界面

### 8.1 入口（见决定点 D2）

导航新增独立目的地"标签"（D2），默认位于"自动 IPA"与"形态函数"之间，与 IPA、形态两组描述语言的页面相邻；形态匹配依赖标签，顺序上先标签后形态。

- 新目的地加入 `DEFAULT_TOOL_NAV_ORDER`（`lib/dictionary-data-model.js`）；已保存的 `toolNavOrder` 由现有规范化补齐缺项，用户仍可自行调整位置。
- 页面没有需要确认的未保存状态，不接入"保存 / 放弃更改 / 取消"流程。离开页面时，正在编辑的显示名按失焦规则保存。
- "其他设置"的"词条标签"小节整节删除，其中的八项显示偏好移到本页的"显示"面板（8.2）。

导航在矮窗口已出现滚动条（交接文档第 4 节），新增一项约多 50px。该问题按交接文档中已提出的方案（按导航实际高度收紧密度、极矮窗口改用细滚动条与渐隐）单独处理，不以把功能收进设置页来回避；在它解决之前，矮窗口下的滚动条会更早出现。

备选（已放弃）：在"其他设置"页顶部加分页"常规 ｜ 标签"。放弃的理由见 9.8。

"显示"面板中的开关和下拉框改动后立即保存；标签上限输入框按 `Enter` 或失焦保存，超出 2–10 时就地提示并还原。四项"显示原始标签"开关放在显示名附近的面板里，便于对照显示名的效果。

每行：

- **拖动把手**：区内与跨区拖动；词性区为空时显示"拖到这里设为词性"占位。
- **标签芯片**：用实际的标签样式渲染（含红色强调和显示名），即所见即所得的预览；原始值始终可见。
- **显示名**：行内输入框，占位为原始值；`Enter` 或失焦保存，`Esc` 还原；输入法组字中不处理。
- **使用数**：按钮，点击跳到按该标签筛选的词条列表（经现有未保存检查）；为 0 时整行变灰。
- **红色强调**：开关控件（Style Skin Plan 第 2 节"开关"）。
- **更多菜单**：移到顶部、移到底部、设为词性／移出词性、删除（只有未使用的标签可选；在用时禁用并以 tooltip 说明原因）。

顶部：

- **搜索**：按原始值和显示名过滤两个区。过滤时禁用拖动（不相邻的行之间放下位置不明确），更多菜单中的移动仍可用。
- **添加标签**：在普通区末尾出现输入行；值重复时定位到已有行；含分隔符时就地提示。
- **整理已有词条**：括号内为试运行得到的、标签顺序与登记表不一致的词条数，为 0 时禁用（见决定点 D4）。

### 8.3 键盘

- 每个区内只有一个 Tab 停靠点，上下方向键在行间移动（roving tabindex，与阶段 A+ 的方向一致）；行内控件按 Tab 进入。
- `Alt` + `↑`／`↓` 移动当前行，沿用来源卡片的写法；在词性区底部按 `Alt` + `↓` 移入普通区顶部，反之亦然。

### 8.4 窄屏

480px 以下每行折成两行：把手、芯片、使用数／显示名、开关、菜单。触屏不依赖拖动，更多菜单提供全部移动操作。"显示"面板在 1024px 以下的折叠方式见 8.2。

### 8.5 规模

预期标签数在几十到几百。管理页直接渲染全部行，不做虚拟滚动；验收时用生成的 2000 标签词典测量渲染与拖动，若超过可接受范围再改为窗口化。

## 9. 独立复评

把第 1–8 节和此前对话中的草案当作外部提案重新检查。

### 9.1 必要性

- 只做一个可视化编辑器、仍写回四项设置，也能实现拖动排序。但四项设置的匹配规则互不相同（第 2 节），可视化后用户看到的是"一行一个标签"，背后却是四份可能互相矛盾的列表，例如一个词性可以不在排序里、红色强调写的是显示名。合并成一张表是消除这类不一致的必要条件，不只是界面需求。**结论：保留合并。**
- "新标签自动登记"若只在读取时补齐（不存储），未登记标签的位置只能按字典序或首次出现临时计算，新增一个标签就可能改变其他标签的相对位置，不满足"数据稳定"。**结论：必须在写入时登记。**

### 9.2 存储方案：推翻此前"独立 blob"的提议

此前草案建议单独一个 `module_blobs("tags")`，理由是数据量小、只在 JavaScript 中读取。复评后改为关系表：

- 登记发生在**每一次**带新标签的词条保存里，并不低频。blob 方案要在词条保存事务中读出整份 JSON、合并、再写回；关系表只需对新值执行一条插入，唯一性由主键保证。
- 两个标签页同时操作时，blob 的读改写会让一边的登记或拖动覆盖另一边；按操作修改关系表没有这个问题。
- 标签是结构性主数据（决定什么是词性，进而影响筛选、统计和质量检查），符合 `AGENTS.md`"结构性主数据可以 SQL 化"；它也不是复杂配置。
- 放回 settings blob 更不合适：同样是读改写，而且会让每次带新标签的词条保存都改写整块设置。

代价：schema 多一张表，旧库需要处理（第 7.3 节，blob 方案同样需要）。

### 9.3 保存方式与 API 形状

整表替换最简单，但会让过期的页面抹掉新登记的标签；单操作接口与"每次改动立即保存"一一对应，返回完整登记表也让前端无需自己合并。**保留单操作接口。**

### 9.4 身份与匹配规则

统一为区分大小写的原始值，会改变旧排序和红色强调忽略大小写的行为。这些差异只在转换时出现一次（第 7.2 节第 3、4 条），转换之后不再需要两套匹配规则。**保留。**

曾评估的替代方案（2026-10-25 用户否决）：以"NFC + 小写"为比较键，保存与导入时把标签改写为登记表中的规范写法，使全部比较在效果上不区分大小写。代价是导入时合并不同写法、形态模板匹配标签也要改写、需要另做"只改大小写"的操作，并且无法再用大小写区分两个标签。用户决定严格按字符比较（D7）。

### 9.5 删除规则

在用标签若允许删除，下一次保存又会把它登记回普通区末尾，用户看到的效果是"标签跳到了最后"，难以理解。禁止删除在用标签更直接；需要清理时应先改词条，或等待后续的改名／合并功能。**保留禁止（见 D3）。**

### 9.6 耦合与范围

- 涉及前后端约 50 处读取点，但大多是把"读 settings 某字段"换成"读排名索引"，集中在 `lib/tag-model.js` 的几个函数里，改动可以收在共享模型中。
- 与形态分配计划的关系：该计划的规则编辑器需要标签词汇，可以直接复用登记表；本计划不依赖它。
- 与释义标签阶段 2 的未提交改动：`definitionTagLayerStates` 须改读登记表，宜先提交阶段 2 的剩余改动再开工。
- 改名与合并、编辑框自动补全不纳入本计划，避免一次改动同时改变词条数据。

### 9.7 验收方式

- 新增 `scripts/check-tag-registry.js` 并纳入 `check-all`：每条写入路径之后登记表覆盖在用标签；新标签登记位置与顺序；四种操作及其错误码；删除在用标签返回 409；移动后 facets、筛选、统计、质量结果随之变化；导出再导入后登记表不变（含灰色行）。
- 旧格式转换在转换契约中验证第 7.2 节的每条规则，包括大小写合并、红色强调写显示名、只在旧配置中出现的值。
- 界面按 `AGENTS.md` 的 UI 验收检查项逐项检查，并在交接文档中列出未完成项。

### 9.8 页面位置：推翻"其他设置分页"的提议（2026-10-25）

初稿推荐把标签管理做成"其他设置"里的分页，主要理由是不增加导航高度。复评后改为独立导航目的地：

- 页面性质不同：它显示使用数和未使用的标签，可以跳到词条，并决定这门语言有哪些词性，属于描述语言的工作区，与自动 IPA、形态函数、形态表格同类；"其他设置"放的是设好后很少再看的显示偏好和行为开关。
- 同一页面两种保存方式：常规分页靠"保存配置"，标签分页即时保存。拆分标签管理的初衷是脱离设置表单的保存流程，分页只在代码上分开，界面上仍然绑在一起；设置页目前也没有分页结构，等于为这一项新造一种页面模式。
- 导航高度是已记录、待视觉审查处理的独立问题，应由该问题的方案解决，不应决定功能放在哪里。

1. **T1 数据与读取路径**：建表；登记写入；单操作端点与读取端点；导入导出与旧格式转换；外键；共享模型改为排名索引；前后端全部读取点切换；facets 词性顺序；质量规则输入；删除设置页"词条标签"整节与保存后的整理询问；契约测试。按工具分工，可由 GPT 依带验收命令的规格实装后端部分，前端读取点由 Claude 处理。
