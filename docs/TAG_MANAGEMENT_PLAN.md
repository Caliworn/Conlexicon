# 标签管理计划

状态：T1、T2 已实现（2026-10-30），待用户验收，通过后本计划删除。仍有效的内容已全部迁出，本文不再维护：数据契约在 API Contract、SQLite Backend Spec 和导入导出规范，页面规范在 [Tag Manager Specification](TAG_MANAGER_SPEC.md)，后续候选在交接文档。第 11 节的决定点 D1–D8 已由用户确认（2026-10-25），D9、D10 已由用户确认（2026-10-27，D9 撤回 D4），D11、D12 与代理拟定的设计选择（T-b–T-l、T-n–T-z）已由用户确认（2026-10-30）。

## 1. 背景与目标

标签相关的配置现在分散在"其他设置"的四个文本框里，随"保存配置"整体提交：词性、排序、显示替换、红色强调。它们各自按不同规则匹配标签，排序只能靠手写列表，筛选菜单里的词性也不跟随排序。

目标：

1. 用一张**有序的标签登记表**取代这四项设置，作为词典标签的唯一配置来源。
2. 登记表分两个区：**词性区**永远排在**普通标签区**之前；放进词性区的标签就是词性。
3. 标签管理页做成独立的导航目的地，**每次改动立即保存**，不进入设置表单的未保存检查和离开确认。"其他设置"中"词条标签"小节的其余显示偏好也全部移到这个页面，设置页不再有标签相关的项。
4. 词条里出现的新标签自动登记到普通区末尾；已登记的标签除非手动删除，否则不会消失；当前没有词条使用的标签显示为灰色。
5. 列表、详情、有效标签、筛选菜单（含词性）、分析页的组合行、导出统一按登记表排序。标签在词条和释义中不再有自己的存储顺序（3.3）。
6. 登记表是标签信息的唯一来源：词性、显示名、红色强调和顺序都由服务端随登记表提供，前端按标签查表，不再自行推导（6.5）。

不在本计划范围内（可作为后续候选）：改名与合并标签（批量改写词条）、编辑框中的标签自动补全、标签颜色多于红色一种（存储字段已按颜色设计，见 3.1、9.11）、管理页压缩视图（8.6）。

## 2. 当前事实（已对照代码确认）

- 四项设置位于 settings 模块（`module_blobs.settings`），由 `lib/dictionary-data-model.js:103-111` 规范化，随设置表单经 `PUT /settings` 保存。该端点是部分更新：服务端把请求体合并进已存设置，IPA 固定保留（`mergeOtherSettings`，`lib/sqlite-dictionary-repository.js:435`）。
- 匹配规则不一致：
  - 词性按结构键（`normalizeStructuralKey`，只去首尾空白、区分大小写）匹配，`lib/tag-model.js` 的 `entryParts`；前端、服务端和质量规则相同；
  - 排序有三套规则：词条显示、保存和摘要 DTO 用 `arrangeTagsByOrder`，按 `normalizeText` 匹配 `tagSortOrder`（忽略大小写），未列出的标签保持存储顺序；分析页的标签组合与词性组合用 `tagDisplayRank`（`lib/sqlite-dictionary-repository.js` 约 2160 行），按结构键匹配（区分大小写），未列出的按 `localeCompare` 字母序；前端筛选菜单的词性列表和服务端 facets `parts` 不读 `tagSortOrder`，按字母序。同一标签在词条和分析页中的先后可能不同；
  - 红色强调同时匹配原始标签和显示替换文本，按结构键比较（区分大小写），`tagIsRedHighlighted`；
  - 显示替换按原始值精确查表，`displayTag`。
- 前后端各自从四项设置推导同一批标签信息：服务端在标签身份快照中算出是否为词性、显示名和显示歧义；前端在 `lib/tag-model.js` 中再判断一次词性、显示名、红色强调和标签顺序，并把四项设置序列化后拼进三处查询缓存键。
- `entry_tags` 与 `definition_tags` 的主键是 `(所属对象, position)`，标签在每个词条和每条释义中有存储顺序。运行期词条写入时服务端先按 `tagSortOrder` 重排再存储（`normalizeEntryForSave`，`lib/sqlite-dictionary-repository.js:3312`）；JSON 导入保持原顺序；`tagSortOrder` 改动后存量词条不会自动更新，由批处理 `applyTagOrder` 整理。
- 有效标签（词条标签与全部释义标签的并集）在显示时按 `tagSortOrder` 排序，前后端共用 `tagModel.effectiveEntryTags`：先按"词条标签在前、释义按顺序"拼出并集，列在 `tagSortOrder` 中的标签按其位置排前，未列出的保持存储顺序。
- 设置保存后若 `tagSortOrder` 有变化，前端试运行批处理并询问是否立即整理（`app.js` 的 `offerTagOrderForExistingEntries`）。
- 筛选 facets（`GET /api/dictionaries/:id/facets`）响应 `{ generation, identities, collisionGroups, parts, tags, noPartOfSpeechCount }`。前端存入查询缓存时只保留 `generation`、`identities`、`collisionGroups`，并从 `identities` 自行推导词性列表、按 `localeCompare` 排序（`app.js` 的 `compactEntryFacetsResult`）；之后只读取 `identities`，`generation` 与 `collisionGroups` 存而不读。服务端的 `parts`、`tags`、`noPartOfSpeechCount` 前端都未使用，只有契约测试断言它们。
- facets 尚未加载或加载失败时，前端退回 `displayTag` 且不标显示歧义（`app.js` 的 `activeTagDisplayIdentity`），同一标签会先显示"名词"、加载后变为"名词 (n)"。
- 摘要 DTO 有两份实现：服务端 `entrySummary` 与前端 `entrySummaryDto`（保存后就地更新列表）各算一遍有效标签、词性和释义预览词性。释义预览中服务端按 `tagSortOrder` 重排，前端按存储顺序取；因保存时已按同一规则存储，目前结果相同。摘要 DTO 的 `partOfSpeech`（`parts[0]`）前端不读取，前端 `entryPart()` 没有调用方。
- 词性判断在前后端有多处副本（前端 `entryParts`、`tagIsPart`、`definitionTagLayerStates`；服务端身份快照、`configuredPartValues`、无词性计数 SQL、质量规则输入），各自读取 `partOfSpeechTags`，比较方式相同。
- 词条搜索为标签同时写入原始值和显示名两条记录（`lib/entry-search-model.js:145`）。`tagDisplayMap` 变化时，`PUT /settings` 重建整个词条搜索投影（`staticSearchProjectionSettingsKey`）。
- 语料块、语料层、语料单元的 `tags` 只作为文本编辑和搜索使用，不做显示替换、红色强调或词性判断。
- 每个标签的使用词条数已有缓存：`entryTagIdentitySnapshotFromDatabase`（同文件 2007 行），按查询会话 generation 失效。
- 运行期词条的标签行只在 `writeEntryProjection` 写入；JSON 导入走另一处批量写入（同文件约 3963 行）。
- 质量规则只读取 `partOfSpeechTags`（`qualityInputSettings`）；形态模板匹配不读取这四项设置。标签类质量规则中：`near_duplicate_tags` 按小写并去掉非字母数字字符后分组，是全局问题；`tag_too_long` 按每个词条、每次出现各报一条。
- 分析页的词性分布与标签频率按词条数排序，只包含有词条在用的标签。
- 标签输入框按半角逗号、全角逗号和顿号拆分（`parseTagListText`），界面无法输入含这三种字符的标签；但数组形式的写入与导入既不拆分也不校验（`normalizeTagList` 只去空白和完全相同的重复值），已有数据中可能存在这类标签。
- 形态模板组的 `matchTags` 以 JSON 存放标签值（`match_tags_json`），与 `entry_tags`、`definition_tags` 没有引用关系。
- 标签层级标注与三条标签层级质量规则共用的 `definitionTagLayerStates`（`lib/tag-model.js`，2026-10-25 新增）也读取 `partOfSpeechTags`；实施时须一并改为读取登记表。

## 3. 数据模型

### 3.1 存储

新增关系表（第 9.2 节说明为什么不用 blob）：

```sql
CREATE TABLE tag_registry (
  tag TEXT PRIMARY KEY,                       -- 原始标签值，已去首尾空白
  part_of_speech INTEGER NOT NULL,            -- 1 = 词性区，0 = 普通区
  position INTEGER NOT NULL,                  -- 区内顺序，从 0 连续
  display_label TEXT NOT NULL DEFAULT '',     -- 空 = 显示原始值
  color TEXT NOT NULL DEFAULT '',              -- 颜色名；空 = 默认样式，当前合法值只有 red
  UNIQUE (part_of_speech, position)
);
```

**颜色字段**：红色强调存为 `color = 'red'`，不用布尔列。多色功能不在本计划范围内，但改表结构要再走一次导出导入迁移（7.3），所以字段现在就按颜色设计；当前界面仍是开关（8.2），接口也只接受 `''` 与 `red`（9.11）。

**标签不设代理 ID**：标签值本身就是主键。词条和释义一直按值引用标签（`entry_tags.tag`、`definition_tags.tag`），不需要另一层身份；代理 ID 会要求两张标签表改为按 ID 引用，牵动搜索投影、筛选和导入导出，本计划没有需要它的功能。

`entry_tags.tag` 与 `definition_tags.tag` 增加外键 `REFERENCES tag_registry(tag)`（不级联删除）。这样不变量 1（下一节）和"在用标签不能删除"都由数据库约束保证；两张表已有以 `tag` 开头的索引（`idx_entry_tags_tag_entry`、`idx_definition_tags_tag_entry`），删除登记行时的外键检查不需要全表扫描。写入顺序随之确定：先登记，再写标签行。

两张标签表同时去掉 `position` 列，标签在词条和释义中是集合（3.3）：

```sql
CREATE TABLE entry_tags (
  entry_id TEXT NOT NULL REFERENCES entries(id) ON DELETE CASCADE,
  tag TEXT NOT NULL REFERENCES tag_registry(tag),
  PRIMARY KEY (entry_id, tag)
);

CREATE TABLE definition_tags (
  definition_id TEXT NOT NULL,
  entry_id TEXT NOT NULL,
  tag TEXT NOT NULL REFERENCES tag_registry(tag),
  PRIMARY KEY (definition_id, tag),
  FOREIGN KEY (definition_id, entry_id) REFERENCES definitions(id, entry_id) ON DELETE CASCADE
);
```

新主键同时由数据库保证同一词条或同一释义内的标签不重复。

`UNIQUE (part_of_speech, position)` 在 SQLite 中逐行检查，整体平移 `position` 的单条 `UPDATE` 会中途冲突（已实测）。移动和删除时先把受影响行写成负数临时值，再写回目标值，两步在同一事务内。

`partOfSpeechTags`、`tagSortOrder`、`tagDisplayMap`、`redHighlightTags` 从 settings 中移除。其余八项标签显示偏好不是逐个标签的数据，仍存于 settings，但改由标签管理页编辑，经 `PUT /settings` 保存（第 6.4 节）：

| 字段 | 含义 |
| --- | --- |
| `tagListSeparatorStyle` | 标签输入框重新显示时的分隔符 |
| `entryListRawTagDisplay` | 词条列表的标签行显示原始标签 |
| `entryListRawPartDisplay` | 词条列表的词性文本（副标题和释义前）显示原始标签 |
| `filterMenuRawTagDisplay` | 筛选菜单中显示原始标签 |
| `entryHoverCardRawTagDisplay` | 词条悬浮卡片中显示原始标签（2026-10-25 新增） |
| `entryListTagDisplayLimit` | 词条列表中标签显示上限（2–10，默认 3） |
| `entryListTagsIncludeParts` | 词条列表的标签行包含词性标签 |
| `entryListTagFiltering` | 在词条列表中点击标签时按标签筛选 |

### 3.2 不变量

1. **登记表覆盖全部在用标签**：`entry_tags` 与 `definition_tags` 中出现的每个值都在 `tag_registry` 中。由外键保证，写入路径在同一事务内先登记新值（第 4 节），不靠读取时补齐。
2. **只增不减**：除了在管理页手动删除，任何操作都不删除登记行；删除词条、改写标签后旧标签留在表中，变为灰色。
3. **顺序显式**：每个区内 `position` 唯一且连续。
4. **身份按原始值**：标签身份是去首尾空白后的原始字符串，逐字符比较，不做大小写折叠或 Unicode 规范化，与有效标签、词性筛选和形态匹配一致。`Noun` 与 `noun` 是两行（D7）。
5. **顺序只有一个来源**：标签的先后只由登记表决定。词条和释义只记录有哪些标签，不记录顺序（3.3）。

### 3.3 排序规则

标签的排名 = 词性区按 `position`，然后普通区按 `position`。共享模型提供 `tagRank(registry)`，凡是需要列出多个标签的地方都用它排序：词条标签、每条释义的标签、有效标签、分析页的组合、导出 JSON 中的标签数组。

- **不存储逐词条顺序**（D9）：有了登记表，每个标签都有排名，显示时不会再出现"规则未覆盖、按存储顺序兜底"的标签；存储顺序若保留，只会是一份可能过期的冗余副本。若改为"存储顺序必须遵守规则"，登记表里每次拖动都要改写所有用到该标签的词条和释义，与"每次改动立即保存"冲突。因此去掉两张标签表的 `position` 列（3.1），读取时按排名排序。
- **有效标签**：词条标签与全部释义标签的并集，按排名排序。原先"词条标签在前、释义按顺序"的先后不再体现在有效标签里；词条与释义两层的区别由详情和编辑器分层显示。
- **尚未登记的标签**（只在未保存的草稿、快速录入预览中出现）排在所有已登记标签之后，保持输入顺序；这与保存时登记到普通区末尾的结果一致（第 4 节）。
- **编辑框**：输入过程中保持输入顺序，保存后重新渲染时按排名显示。判断编辑是否有改动时，标签按集合比较，只调整输入顺序不算改动。
- **规范序**：服务端内部的标签数组（保存响应、读取结果、搜索记录、质量输入）一律按标签值的二进制序，使保存响应与之后的读取结果相同，也使搜索记录的 `source_position` 不随登记表变化。规范序没有业务含义，不用于显示。

## 4. 登记规则

| 来源 | 行为 |
| --- | --- |
| 运行期词条写入（新建、保存、`PATCH /entries`、创建或绑定来源时改写的词条、整词典批处理） | `writeEntryProjection` 写标签行之前，把未登记的值 `INSERT` 到普通区末尾。同一次写入里的多个新标签按出现顺序登记：词条标签在前，然后按释义顺序 |
| 快速录入 | 经同一保存端点，规则同上 |
| JSON 导入（当前格式） | 文件中的 `tagRegistry` 原样写入（边界校验），再把文件中在用但未登记的标签按首次出现追加到普通区末尾。词条和释义中标签数组的顺序只用于决定这些新标签的登记先后，不写入标签表 |
| JSON 导入（旧格式，无 `tagRegistry`） | 由旧数据转换生成登记表，见第 7.2 节 |
| 管理页手动添加 | 添加到所选区的末尾，使用数为 0，显示为灰色 |

新标签一律进普通区，不会自动成为词性。

| 位置 | 改动 |
| --- | --- |
| 词条列表、悬浮卡片、衍生词卡片、详情头部与释义标签、词汇网络节点、编辑框 | 显示前按排名排序 |
| 保存 | 不按排名排序；标签表只记录集合，标签数组规范为二进制序（3.3） |
| 导出 | 词条和释义的标签数组按排名输出 |
| 筛选菜单与排序菜单的词性胶囊 | 按登记表顺序列出词性区的标签，由服务端随登记表提供，前端不再从 facets 推导和排序（6.5） |
| 词性判断（筛选 `part`／`partCount`／`partSet`、统计、多词性分析、质量规则、卡片上的词性分层、标签层级标注） | 词性集合 = 词性区的标签 |
| 分析页标签组合与词性组合行 | 组合内的标签按排名排列，删除 `tagDisplayRank`，与词条显示使用同一排名；行本身仍按词条数排序 |

| 分析页标签频率与词性分布 | 每行在"筛选词条"之外增加"在标签管理中查看"（T-v） |
| 质量规则 `mixed_part_of_speech_levels`、`missing_definition_part_of_speech` 与标签层级标注 | 词性集合 = 词性区的标签，质量输入从 `partOfSpeechTags` 改为词性区的值 |
| 质量规则 `near_duplicate_tags` | 增加跳转到标签管理页并高亮相关行的动作（T-w） |
| 新质量规则"显示名冲突" | 全局、低严重度，动作跳转到标签管理页（T-x）；质量输入增加登记表 |
| 质量规则 `tag_too_long` | 改为每个标签报一条的全局问题（T-y） |
| 显示替换、红色强调 | 读登记行的 `displayLabel`、`color`，按原始值精确匹配 |
| 标签搜索 | 仍为原始值和显示名各建记录；显示名改动只更新用到该标签的词条的搜索记录（6.2） |
| 摘要 DTO | 服务端 `effectiveTags`、`parts` 与释义预览的 `parts` 不再排序，由前端按排名排列（6.5）；删除前端不读取的 `partOfSpeech` 字段与前端无调用方的 `entryPart()`；前端 `entrySummaryDto` 与保存后的列表就地更新已删除（2026-10-30），列表由保存后的重新查询刷新 |
| 形态模板匹配 | 不变，只看标签值 |
| 语料块、语料层、语料单元的标签 | 不进入登记表，保持现状：不做显示替换、红色强调或词性判断，不受外键约束 |

在登记表里调整顺序只改登记表，不改写任何词条；所有显示随即按新顺序排列。

## 6. API

### 6.1 读取

登记表的内容分两类读取：标签配置（是否为词性、显示名、红色强调、顺序）随词典状态一次给出；使用数是查询结果，每次词条保存都会变，按查询会话 generation 缓存。

- `GET /api/dictionaries/:id` 增加 `tagRegistry: { tag, partOfSpeech, displayLabel, color, displayAmbiguous }[]`，按排名排列（数组顺序即顺序，不暴露 `position`）。`displayAmbiguous` 由服务端在整张登记表范围内计算（显示名与其他行的原始值或显示名相同）。前端进入状态时据此建立查表索引（6.5），替代原先读取四项设置的位置。
- `GET /api/dictionaries/:id/tag-registry`：`{ id, generation, tags }`，行与上述字段相同，另加 `entryCount`（按有效标签计数，0 即灰色）。行内容每次从登记表读取，只有计数复用标签身份快照；修改颜色不使快照失效，不能从快照取颜色。管理页和筛选菜单都读取它。
- **facets 端点退役**：`GET /api/dictionaries/:id/facets` 删除。它提供的标签身份（显示名、是否为词性、显示歧义）改由 `tagRegistry` 提供，使用数改由上一条端点提供；`parts`、`tags`、`collisionGroups`、`noPartOfSpeechCount` 前端都未使用（第 2 节），不迁移。筛选菜单与排序菜单的词性选项 = 登记表词性区中 `entryCount > 0` 的行，按登记表顺序。

### 6.2 修改

`POST /api/dictionaries/:id/tag-registry/changes`，请求体是**单个操作**，返回 `{ id, updatedAt, tagRegistry }`（含计数，与读取端点同形）：

| 操作 | 请求体 | 说明 |
| --- | --- | --- |
| 添加 | `{ op: "add", tag, partOfSpeech }` | 加到该区末尾 |
| 移动 | `{ op: "move", tag, partOfSpeech, before }` | `before` 为同区的另一个标签，或 `null` 表示该区末尾；跨区移动即改变是否为词性 |
| 修改 | `{ op: "update", tag, displayLabel?, color? }` | 只改给出的字段；显示名与该标签自身的原始值相同时存为空（T-r） |
| 删除 | `{ op: "delete", tag }` | 只允许删除没有词条使用的标签 |

用操作而不是整表替换，是为了让多个标签页同时打开时，一边拖动不会抹掉另一边刚登记的新标签。

错误码：`tag_registry_invalid_tag`（空值或含分隔符）、`tag_registry_tag_exists`、`tag_registry_tag_not_found`、`tag_registry_anchor_not_found`（`before` 不在目标区）、`tag_registry_tag_in_use`（删除在用标签，409，`details.entryCount`；服务端在同一事务内先计数再删除，外键是最后一道约束）、`invalid_tag_registry_change`（请求体格式无效，包括 `color` 不是合法颜色名）。

每次修改都推进词典 `updatedAt`，前端据此刷新登记表（6.5）。服务端派生数据按操作影响的内容分别更新：

| 操作 | 查询会话（筛选、统计、分析、质量） | 词条搜索记录 |
| --- | --- | --- |
| 添加、删除 | 失效（使用数和登记表行变化） | 不变 |
| 移动，区内 | 失效（分析页组合内顺序由服务端排列） | 不变 |
| 移动，跨区（改变是否为词性） | 失效 | 不变 |
| 修改显示名 | 失效（分析页、身份快照带显示名） | 在同一事务内更新该标签的显示名记录：它们的 `raw_value` 是显示文本，通过同一定位（词条、来源类型、来源 ID、位置）上的原始值记录找到；不重建整个投影 |
| 修改颜色（红色强调） | 不失效（只影响前端显示） | 不变 |

质量结果只在跨区移动时实际变化，其余操作使会话失效后重新计算得到相同结果；不为质量结果另设失效规则。

### 6.3 其他端点的变化

- 词条写入类端点：本次写入登记了新标签时，响应额外带 `tagRegistry`（不含计数），前端整体替换状态中的登记表；没有新标签时不带。
- `PUT /settings`、带 settings 的 `PATCH /entries`：不再涉及四项设置。
- 批处理 `applyTagOrder`：删除。标签表不再存储顺序（3.3），没有需要整理的内容（D4 撤回，见 D9）。设置保存后的整理询问随四项设置一起删除。

### 6.4 标签显示偏好

不新增端点。标签管理页的"显示"面板每改一项，就以 `PUT /settings` 发送只含该字段的请求体；服务端合并进已存设置，其余设置不受影响。"其他设置"表单删去这八项后不再发送它们，已存的值由同一合并规则保留，不需要额外的保留或忽略规则。前端用响应中的 settings 替换状态，与现有设置保存相同。

代价：`PUT /settings` 每次都会使该词典的查询会话失效，而这八项只影响前端显示，切换一次会让下一次查询重新计算。这些偏好很少修改，接受这一开销，不为它另设端点。

### 6.5 前端职责

登记表中的每一行已经是现成的事实，前端只做查表，不再从设置推导标签信息：

- **查表**：进入词典状态、或写入响应带回 `tagRegistry` 时，建立一个 `Map(tag → { rank, partOfSpeech, displayLabel, color, displayAmbiguous })`。词性判断、显示名、红色强调、显示歧义和排序都读它，按原始值精确匹配。登记表随词典状态一起到达，不再有"facets 未加载时不标显示歧义"的过渡状态（第 2 节）。
- **未登记标签的默认值**：草稿和快速录入预览中尚未保存的标签不在表中，按"普通区末尾、无显示名、不是词性、不红、无歧义"处理，与保存时的登记结果一致（第 4 节）。标签层级标注（`definitionTagLayerStates`）在编辑时也据此判断是否为词性。
- **排序**：比较函数放在共享模型 `lib/tag-model.js`（`tagRank`）。前端用它在渲染时排列所有标签，已保存词条和草稿共用；服务端只在需要最终顺序的地方用它，即导出和分析页的组合，列表与详情数据保持规范序（3.3）。这样登记表移动后，前端已缓存的列表页不会显示过期的顺序。
- **不再进行的推导**：从 facets 过滤和排序词性列表、`arrangeTagsByOrder` 的排名计算（含其忽略大小写的匹配）、红色强调同时比对原始值与显示名、把四项设置序列化进查询缓存键。登记表修改会推进词典 `updatedAt`，已含 `updatedAt` 的查询缓存键（`entryQueryApiKey`、原 `entryFacetsApiKey`）直接删去这部分。`entryCardSettingsSizeSignature` 不含 `updatedAt`，改用登记表的签名：建立查表索引时序列化一次并保存，不在每次计算尺寸时重新序列化。

## 7. 导入、导出与旧数据

### 7.1 导出与当前格式导入

导出 JSON 顶层增加 `tagRegistry`（含灰色行），往返保持不变。词条和释义的 `tags` 数组仍是数组，按排名输出；导入时只取其中的集合。导入在边界校验：值非空、无重复、字段类型正确、`color` 是合法颜色名；不合规整次拒绝。这里不校验分隔符：已有数据可能含这类标签（第 2 节），校验会让导出的文件无法再导入。分隔符只在管理页 `add` 操作时拒绝。

### 7.2 旧格式转换

由 `lib/legacy-dictionary-migration.js` 负责，输入为四项旧设置与词典中实际在用的标签：

1. **词性区**：`partOfSpeechTags` 中的标签。先按在 `tagSortOrder` 中的位置，未列出的按 `partOfSpeechTags` 原顺序排在后面。
2. **普通区**：`tagSortOrder` 中的非词性项按原顺序；其余在用标签按首次出现（词条顺序，词条标签在前、释义标签在后）。
3. **大小写**：旧排序忽略大小写（词性和红色强调区分大小写，见第 2 节）。一项旧排序配置匹配到多个在用值（如 `Noun` 匹配 `noun` 与 `NOUN`）时，这些值共享该位置，按首次出现排列。
4. **红色强调**：旧配置可能写的是显示替换文本，按"原始值或显示文本"解析为原始值，对应行写入 `color: "red"`。
5. **没有对应在用标签的旧配置**（只出现在词性、排序、显示替换或红色强调里的值）登记为灰色行，保留原有设置，不丢弃。
6. 转换后 settings 中不再保留四项旧字段。
7. **逐词条顺序**：旧数据中标签数组的顺序只用于第 2 条的"首次出现"，不保留到标签表。

可见变化：
- 原排序把非词性标签排在词性前面的词典，转换后词性会移到最前；这是"词性永远在前"规则的直接结果。
- 原先没列进 `tagSortOrder`、按存储顺序显示的标签，转换后在每个词条中都按登记表顺序显示。

### 7.3 已有 SQLite 词典

已有 SQLite 词典通过导出导入迁移：用实施前的版本导出 JSON，更新后在词典管理中导入，登记表由第 7.2 节的转换生成。不提供转换脚本，也不在启动时自动升级（`AGENTS.md`），与 2026-10-25 释义标签更新的做法相同。新代码打开旧库时，`tag_registry` 会被建成空表，旧的标签表仍有 `position NOT NULL`，写入标签会失败；不会损坏数据，但词典不可正常使用，因此必须先导出。README 的数据存储一节同步写明这一步。

### 8.6 后续候选：压缩视图

不在本计划范围内。标签特别多时，管理页可增加一种只用于排序的视图：每个标签只显示原始值，一行多个，随宽度换行，拖动排序。

- 数据与接口不变：`move` 操作按"放到哪个标签之前"表达，与一列或多列无关。原始值唯一，不需要处理显示歧义；灰色和颜色不占宽度，可以保留。
- 来源卡片（`renderSourceReferenceTokens`）已有换行排列的拖动：最近插入位置、竖线标记，以及 `Alt` 加方向键按前后顺序移动，可沿用这套做法。
- 窗口化依赖等高的行，难以用于宽度不一的换行标签；压缩视图每项 DOM 更轻，是另一种应对规模的方式（8.5）。

开工前须设计：

1. 触屏：原生拖放在触屏上基本不可用，视图里也没有把手和菜单按钮的位置；可让点击标签打开与完整行相同的更多菜单，同时作为键盘入口。
2. 长距离拖动：起点和终点可能隔好几屏，需要靠近边缘时自动滚动。
3. 行尾放置：一行末尾与下一行开头是同一顺序位置，标记的显示位置需要规则。
4. 长标签：限制最大宽度，用省略号显示，完整内容放在 tooltip 中，320px 下不撑破布局。
5. 视图选择的保存位置：`PUT /settings` 每次都会使查询会话失效（6.4），不适合；更接近全局界面偏好（`data/index.json`）或进程状态。

## 9. 独立复评

把第 1–8 节和此前对话中的草案当作外部提案重新检查。

### 9.1 必要性

- 只做一个可视化编辑器、仍写回四项设置，也能实现拖动排序。但四项设置的匹配规则互不相同（第 2 节），可视化后用户看到的是"一行一个标签"，背后却是四份可能互相矛盾的列表，例如一个词性可以不在排序里、红色强调写的是显示名。合并成一张表是消除这类不一致的必要条件，不只是界面需求。**结论：保留合并。**
- "新标签自动登记"若只在读取时补齐（不存储），未登记标签的位置只能按字典序或首次出现临时计算，新增一个标签就可能改变其他标签的相对位置，不满足"数据稳定"。**结论：必须在写入时登记。**

### 9.2 存储方案：推翻此前"独立 blob"的提议

此前草案建议单独一个 `module_blobs("tags")`，理由是数据量小、只在 JavaScript 中读取。复评后改为关系表：

- 登记发生在**每一次**带新标签的词条保存里，并不低频。blob 方案要在词条保存事务中读出整份 JSON、合并、再写回；关系表只需对新值执行一条插入，唯一性由主键保证。
- 两个标签页同时操作时，blob 的读改写会让一边的登记或拖动覆盖另一边；按操作修改关系表没有这个问题。
- 标签是结构性主数据（决定什么是词性，进而影响筛选、统计和质量检查），符合 `AGENTS.md`"结构性主数据可以 SQL 化"；它也不是复杂配置。
- 放回 settings blob 更不合适：同样是读改写，而且会让每次带新标签的词条保存都改写整块设置。

代价：schema 多一张表，旧库需要处理（第 7.3 节，blob 方案同样需要）。

### 9.3 保存方式与 API 形状

整表替换最简单，但会让过期的页面抹掉新登记的标签；单操作接口与"每次改动立即保存"一一对应，返回完整登记表也让前端无需自己合并。**保留单操作接口。**

### 9.4 身份与匹配规则

统一为区分大小写的原始值，会改变旧排序忽略大小写的行为；红色强调写显示名的旧配置也要解析为原始值。这些差异只在转换时出现一次（第 7.2 节第 3、4 条），转换之后不再需要两套匹配规则。**保留。**

曾评估的替代方案（2026-10-25 用户否决）：以"NFC + 小写"为比较键，保存与导入时把标签改写为登记表中的规范写法，使全部比较在效果上不区分大小写。代价是导入时合并不同写法、形态模板匹配标签也要改写、需要另做"只改大小写"的操作，并且无法再用大小写区分两个标签。用户决定严格按字符比较（D7）。

### 9.5 删除规则

在用标签若允许删除，下一次保存又会把它登记回普通区末尾，用户看到的效果是"标签跳到了最后"，难以理解。禁止删除在用标签更直接；需要清理时应先改词条，或等待后续的改名／合并功能。**保留禁止（见 D3）。**

### 9.6 耦合与范围

- 涉及前后端约 50 处读取点，但大多是把"读 settings 某字段"换成"查登记表"，集中在 `lib/tag-model.js` 的几个函数里，改动可以收在共享模型中。
- 与形态分配计划的关系：该计划的规则编辑器需要标签词汇，可以直接复用登记表；本计划不依赖它。
- 与释义标签阶段 2 的未提交改动：`definitionTagLayerStates` 须改读登记表，宜先提交阶段 2 的剩余改动再开工。
- 改名与合并、编辑框自动补全不纳入本计划，避免一次改动同时改变词条数据。

### 9.7 验收方式

- 新增 `scripts/check-tag-registry.js` 并纳入 `check-all`：每条写入路径之后登记表覆盖在用标签；新标签登记位置与顺序；四种操作及其错误码；删除在用标签返回 409；移动后词条显示顺序、导出顺序、筛选、统计、质量结果随之变化，且没有改写任何词条；同一词条或释义内重复标签被主键拒绝；导出再导入后登记表不变（含灰色行）。
- 原先断言 facets 字段的契约测试改为断言 `tag-registry` 读取端点的行与 `entryCount`，`generation` 推进的检查随之迁移。
- 同一组标签在词条显示与分析页组合中的先后相同，包括只差大小写的标签。
- 保存响应与之后读取到的标签数组相同；含分隔符的标签能完成导出再导入；区内和跨区移动、删除后 `position` 连续。
- 修改显示名后，按新显示名能搜到用到该标签的词条、按旧显示名搜不到，其他词条的搜索记录不被改写；修改颜色不使查询会话失效。
- 跨区移动后，`mixed_part_of_speech_levels`、`missing_definition_part_of_speech` 与分析页词性分布随之变化。
- 旧格式转换在转换契约中验证第 7.2 节的每条规则，包括大小写合并、红色强调写显示名、只在旧配置中出现的值。
- 界面按 `AGENTS.md` 的 UI 验收检查项逐项检查，并在交接文档中列出未完成项。

### 9.8 页面位置：推翻"其他设置分页"的提议（2026-10-25）

初稿推荐把标签管理做成"其他设置"里的分页，主要理由是不增加导航高度。复评后改为独立导航目的地：

- 页面性质不同：它显示使用数和未使用的标签，可以跳到词条，并决定这门语言有哪些词性，属于描述语言的工作区，与自动 IPA、形态函数、形态表格同类；"其他设置"放的是设好后很少再看的显示偏好和行为开关。
- 同一页面两种保存方式：常规分页靠"保存配置"，标签分页即时保存。拆分标签管理的初衷是脱离设置表单的保存流程，分页只在代码上分开，界面上仍然绑在一起；设置页目前也没有分页结构，等于为这一项新造一种页面模式。
- 导航高度是已记录、待视觉审查处理的独立问题，应由该问题的方案解决，不应决定功能放在哪里。

### 9.9 存储顺序：去掉逐词条顺序（2026-10-27）

此前草案保留标签表的 `position`，保存时按排名存储，并保留整理存量词条的批处理（原 D4）。复评后去掉逐词条顺序：

- 现在存储顺序的实际作用是给规则没覆盖的标签兜底。登记表让每个标签都有排名，兜底不再发生，存储顺序只剩编辑框文字和导出两处可见，而这两处也可以按排名输出。
- "存储顺序必须遵守规则"有两种做法，都不成立：拖动时同步改写用到该标签的全部词条和释义，会让每次拖动变成整词典写入、触发查询会话失效，与即时保存的管理页冲突；不同步改写，存储顺序就会过期，又要靠批处理追平。
- 去掉后，同一对象内标签不重复改由主键保证，`normalizeEntryForSave` 不再排序，`applyTagOrder` 与设置保存后的整理询问一并删除，代码净减少。
- 失去的能力：单个词条无法表达自己的标签顺序。登记表本身已经让每个标签都有全局排名，这种表达在显示上已不存在，去掉存储顺序没有额外损失。
- 迁移：表结构变化与登记表同属一次导出导入迁移（7.3），不增加步骤。

**结论：去掉 `position`，撤回 D4（D9）。**

### 9.10 前端不再推导、facets 退役（2026-10-27）

- 登记表每行已经给出是否为词性、显示名、红色强调和顺序，前端再从设置推导是重复劳动，并且两边规则可能分叉（第 2 节的排序就与词性、红色强调的比较方式不同）。前端改为查表（6.5）。
- 草稿中的未登记标签无法由服务端提供信息，前端必须有默认值；默认值与保存时的登记规则相同，不构成第二套规则。
- facets 实际被读取的只有 `identities`，其内容与登记表加使用数完全重合。保留两个端点会让同一批行有两种形状，因此并入 `tag-registry` 读取端点（6.1）。
- 使用数与标签配置分开下发：配置只在登记表修改时变化，随词典状态给出即可；使用数随每次词条保存变化，属于按 generation 缓存的查询结果。

### 9.11 颜色字段（2026-10-30）

`red_highlight` 改为 `color`，只改数据形状，不增加本计划的界面和样式工作：

- 必要性：多色功能不一定会做，但本项目没有 schema 迁移链，改列要所有词典再导出导入一次；现在改只多一条校验，第一版工作量基本不变。
- 代价：如果多色功能最终不做，只有一个合法值的文本列比布尔列略多余。
- 边界：`color` 只影响前端显示，失效规则与红色强调相同（6.2）；当前样式仍使用 `--ui-danger` 系列变量，不新增皮肤变量。

**结论：字段用 `color`，合法值暂为 `''` 与 `red`，界面保持开关（D11）。**

### 9.12 开工前复核（2026-10-30）

逐项对照代码复核，修正如下：

- 标签数组需要有确定的规范序，否则保存响应、读取结果和搜索记录会各不相同（3.3）。
- "服务端不排序"的理由原先写的是避免规则写两份，但比较函数本来就在共享模型里，而且导出和分析页必须在服务端排序。保留这一选择的理由改为避免缓存的列表页显示过期顺序（6.5、T-o）。
- 缓存键不能一律改为词典 ID 与 `updatedAt`：`entryCardSettingsSizeSignature` 不含 `updatedAt`（6.5）。
- 导入校验分隔符会破坏导出再导入，改为只在 `add` 操作校验（7.1）。
- 区内移动不能用单条 `UPDATE` 平移 `position`（3.1）。
- 读取端点的行不能取自身份快照，否则修改颜色后读到旧值（6.1）。
- 显示名记录不能按自身的 `raw_value` 定位，局部更新改为通过同一定位上的原始值记录找到（6.2）。

未发现需要推翻 D1–D12 的问题。

### 代理拟定的设计选择（用户已确认，2026-10-30）

- **T-b** 转换后词性强制排在最前，会改变部分词典的现有显示顺序（7.2）。
- **T-c** 跨区移动不弹确认；改动可再拖回。第一版不做带"撤销"的提示。
- **T-d** 搜索过滤时禁用拖动，只保留菜单中的移动操作。

- **T-h** 点击使用数跳到按该标签筛选的词条列表。
- **T-i** 本计划内红色强调保持开关（D11）。日后做多色功能时采用固定色板、存颜色名，不存十六进制色值：一个固定色值无法同时适配浅色和深色，半透明皮肤上的对比度也无法保证。每种颜色在皮肤文件中定义专用变量，红色从 `--ui-danger` 拆出；样式须覆盖普通标签、词性标签和详情里的两种样式，并决定是否扩展到悬浮卡片、词汇网络和分析页（目前都没有红色强调）。

- **T-q** 标签配置（随词典状态）与使用数（`tag-registry` 读取端点）分开下发，使用数按查询会话 generation 缓存（6.1）。

- **T-y** 质量规则 `tag_too_long` 从"每个词条每次出现报一条"改为"每个标签报一条"的全局问题，列出用到它的词条。这会改变现有报告的条数与形状。
