# Definition Tag Specification / 释义标签规范

状态：现行规范。释义可以带标签，多词性的词可以把词性分别放在各条释义上。本文记录数据原则、编辑与显示规则、标签层级的标注、分析入口和设计取舍。存储、DTO、有效标签、规范序与显示顺序、使用范围、搜索投影和质量规则的接口契约以 [API Contract](API_CONTRACT.md) 的“释义标签与有效标签”和质量规则为准；schema 见 [SQLite 后端规范](SQLITE_BACKEND_SPEC.md)；标签显示偏好见 [Tag Manager Specification](TAG_MANAGER_SPEC.md) 的显示面板。

本规范由释义标签计划（2026-10-23 起草，2026-10-25 实施，2026-11-18 完成后删除）整理而来；决定编号（S、U、V 系列）、实施过程和当时的复评都在 Git 历史和 `CHANGELOG.md` 里。

## 1. 数据原则

- **只向上继承**：释义不继承词条标签。词条标签描述这个词，释义标签描述那条释义；需要“整个词”的答案时取两层的并集，即**有效标签**。
- **词性放哪一层是使用约定**：要么只挂在词条上，要么挂在每条释义上；多词性词条原则上放在各条释义上，单词性词条挂在词条上就是合法的。程序不强制、不迁移，也不提供提升或下放标签的批量操作；不符合约定的释义由质量检查报告（第 4 节）。
- **同形异义词只表示偶然同音**：一个词有多个词性或多套变化表时，仍是一个词条，不拆分。
- **一条释义可以只有标签**：释义文字、例句和备注都为空也合法。
- **不做释义级共现筛选**：筛选只看有效标签，不能筛“同一条释义同时带 A 和 B”。这是会让复杂度翻倍的部分。
- 标签的显示顺序只由标签登记表决定（词性区在前，区内按登记顺序），两层都一样，见 API 契约“显示顺序”。

## 2. 编辑

### 2.1 完整编辑与局部编辑

- 每条释义有一个释义标签输入框，形式与词条标签相同：分隔符分隔的文本，三种分隔符都支持。
- 输入框常显，与释义文字同一行并排在它左侧，和详情里标签排在释义文字之前一致；640px 以下排在释义文字上方。
- 两个输入框都不显示标题和说明文字：标签框的占位符为“标签 / Tags”，无障碍名称为“释义标签 / Definition Tags”；释义文字框的无障碍名称为“释义 / Definition”。
- 新增释义时不预填任何标签。释义标签输入不提供 `Tab` 填充，`Tab` 保持普通的焦点移动。
- 编辑器里不显示标签来源和重复的标记（第 3.2 节），保存时也不处理两层重复。标签输入是纯文本，要逐个着色须先改成芯片式输入，那是另一项编辑器改动。
- `allowEmptyTags` 关闭时，保存要求有效标签非空；局部编辑词条基础区时，这项校验读取已缓存的释义标签。

### 2.2 快速录入

- **释义标签开关**：在浮层底栏左侧、按键提示之前，是开关控件，文字为“释义标签 / Definition Tags”。快捷键 `Ctrl`/`Cmd` + `/`，按“/”字符匹配，所以需要 Shift 才能打出“/”的键盘布局同样可用。
  - 开启时每个释义行之前都有一行“释义 N 标签”，之后新增的释义也自动带一行。
  - 只要有任何一行释义标签有内容，开关就不能关闭：开关呈禁用状态，tooltip 说明“清空所有释义标签后才能关闭”；此时按快捷键不切换，在消息行说明原因。全部为空时可以关闭，关闭只是隐藏这些空行。
  - 切换后焦点回到原字段，原字段被隐藏时回到同一条释义。
  - 开关状态只存在内存中，在本次页面会话内跨快速录入草稿保留，不持久化。
- **键盘流程**：`Enter` 依次经过“释义标签 → 释义”；在释义上按 `Enter` 新起一对“释义标签 + 释义”；空的多余释义按 `Backspace` 删除时，连同它的空标签行一起删除。
- **`Tab` 填充**：释义标签行为空时按 `Tab` 填入建议，与词条标签、读音相同。建议来自同一草稿中最近一个有内容的上方释义标签行的全部标签；第一条释义的标签行没有建议。
- **提交与转入完整编辑**：释义标签成为对应释义的标签；“完整编辑”把释义标签一起带进完整编辑器草稿。

## 3. 显示

### 3.1 释义与卡片

- 详情中的释义显示自己的标签，放在释义文字之前、同一行，读起来像“adj. 红色的”：词性用词性徽章样式，其他用描边芯片。只有标签的释义只显示编号和标签，不加占位文字，也不会被“内容为空”的规则隐藏。
- 搜索命中释义标签、且开启了搜索高亮时，详情中高亮命中的那个释义标签芯片（与列表相同的 `mark` 样式），不额外滚动。
- 点击详情中的标签芯片按标签值筛选（词条列表里的芯片是否可点由显示面板的“点击标签时筛选”决定）。筛选本来就按有效标签，所以点释义里的芯片和点头部的芯片结果相同。
- **词性在卡片里的分层**：
  - 词条列表卡片和悬浮卡片的副标题显示词条级词性。
  - 凡是显示释义文字的地方，每条释义前显示这条释义自己的词性，单条释义也显示：只取该释义标签中的词性，按登记表排序、用显示名，多个用 `/` 连接；样式与列表副标题相同的弱化粗体，放在编号之后、释义文字之前，不加句点。只有标签的释义没有释义文字，不列入，编号也不为它留位。
  - 词条列表和悬浮卡片始终列出全部释义，多条时编号。
  - 词汇网络节点、详情和完整编辑中的衍生词卡片显示词条与所有释义的词性并集，按登记表排序、用显示名；来源补全和区分同形词的来源卡片也用词性并集。
- 词条列表的标签行用有效标签渲染，不区分标签来源，“标签显示上限”按有效标签计数。标签行是否包含词性、是否显示原始标签等由显示面板的偏好决定（标签管理规范第 5 节）。

### 3.2 标签层级的标注

详情头部显示全部有效标签（词性与非词性），每个标签按来源标出状态：

| 情况 | tooltip 与无障碍文本 | 临时样式 |
| --- | --- | --- |
| 只在词条上 | 无 | 正常 |
| 只在释义上 | “来自释义 / From definitions” | 灰色外侧虚线 |
| 词条和释义都有 | “与释义重复 / Repeats a definition tag” | 红色外侧虚线 |
| 词性只在释义上，而词条另有词性 | “词性层级混用 / Parts of speech on both levels” | 红色外侧虚线 |

释义里的标签：词条也有这个标签时为“与词条重复 / Repeats an entry tag”；词条有词性、而这条释义有词条没有的词性时为“词性层级混用”。两者都用红色外侧虚线。

- 灰色表示信息，红色表示问题，与第 4 节的质量规则对应。显示与质量检查共用 `tagModel.definitionTagLayerStates()`。
- 每种状态都写进 `aria-label`，不能只靠颜色或线型区分。
- 临时样式是芯片外侧 2px 处的虚线轮廓（`outline`），不改芯片自己的边框，所以红色强调的标签上也看得出。具体视觉待视觉定稿统一设计，本规范只定义状态和文案。

## 4. 质量检查

模块都是“标签”，逐条释义报告，规则契约见 API 契约：

- `duplicate_definition_tag`（低）：释义上有与词条相同的标签，词性和非词性都算。
- `mixed_part_of_speech_levels`（中）：词条有词性，而释义有词条没有的词性。
- `missing_definition_part_of_speech`（中）：词条没有词性，这条释义也没有。

三条合起来要求“词性要么只挂在词条上，要么挂在每条释义上”。词条和释义上有同一个词性时只报重复；没有配置词性时后两条不检查。`missing_tags` 只在有效标签为空时报；`near_duplicate_tags` 与 `tag_too_long` 同时检查两层，释义标签的问题带 `definitionId`，详情写成“释义 2：标签文字 / Definition 2: tag”，点击跳到词条。

多词性本身是合法状态，不是质量问题，只在分析页统计。

## 5. 分析与筛选

- “词汇 > 标签”页的词性分布卡片在“无词性”旁显示“多词性词条 N”，点击跳到 `partCount: { min: 2 }` 的筛选。总览卡片请求同一个 widget，但不显示这个计数。
- 同一页在词性分布卡片后有“词性组合”卡片（widget `partSetDistribution`），形式与标签组合卡片相同，包括“再显示 N 项”的分批展开：每行是一组词性芯片加词条数，只统计至少两个词性的组合，点击跳到 `partSet` 筛选。没有多词性词条时显示“暂无多词性词条 / No multi-POS entries”。总览不请求这个 widget。
- 跳转后的筛选标题沿用 `{label}: {value}` 格式：多词性为“多词性词条 / Multi-POS entries”；组合为“词性组合: adj + n + pron”，用 ` + ` 连接、词性用显示名。这两种筛选不提供循环变体。
- `partCount`、`partSet` 的形状与校验见 API 契约。`partSet` 只做“恰好等于”，不复用 `tags: { mode: "exact" }`，因为后者要求词条不带任何额外标签，带“古语”等非词性标签的词条会被漏掉。

## 6. 自动形态的输入

自动形态通过共享的 `morphologyMatchContexts()` 为每条释义构造一个上下文，内容为词条标签与这条释义标签的并集。没有释义时只有词条标签的一个上下文。词条标签进入每个上下文，适合放变化类等词级属性。未标标签的释义只用词条标签。

不同释义的标签各自参与匹配。例如释义 1 有 `n` 和 `古语`，释义 2 有 `v`，两条释义都不满足同时要求 `v` 与 `古语` 的规则。各释义生效的表合并去重，用于搜索投影和形态分析。其他按有效标签统计或筛选的功能仍使用词条标签与全部释义标签的并集。[形态分配与保存](API_CONTRACT.md#形态分配与保存)

## 7. 设计取舍

- **为什么做通用释义标签，而不是只给释义加一个“词性”字段**：词性本身就是 `partOfSpeechTags` 定义的标签子集，一改设置，字段里的值就可能不再是词性，还得另外设计失效处理；两者实现成本相近，通用标签反而不用处理设置变化。把词性写进释义文本（如“(adj.) ……”）则无法筛选、统计或参与形态匹配。
- **为什么用独立的 `definition_tags` 表，而不是给 `entry_tags` 加归属列**：新表可以用外键级联到释义，删除释义时标签自动删除；主键含可空列在 SQLite 里语义很弱；分表后词条级查询不会被释义标签意外放大，需要并集的地方显式使用并集片段。表里冗余存一份 `entry_id`，由复合外键保证与释义的归属一致，前提是释义不会在词条之间移动。
- **并集片段为什么不用 `UNION`**：SQL 侧用两段不相交的行表示有效标签（词条标签，加只在释义上出现的标签），不建持久化 VIEW（`IF NOT EXISTS` 不会更新已有的 VIEW 定义）。初版用 `UNION` 时，3 万条压力词典的 facet 和标签组合统计慢了 2–3 倍；改后没有释义标签时与只有词条标签时基本持平。
- **为什么摘要 DTO 另加 `effectiveTags`，而不是把 `tags` 改成并集**：同一个字段名在摘要和详情里含义不同，容易写错。
- **词性组合为什么是独立的 widget**：给标签组合加“只看词性”参数时，同一个 widget 会返回两种分组口径，计数项、跳转筛选和标题都要随参数分叉。
- **搜索投影主键为什么加 `source_id`**：释义标签的 `sourcePosition` 是释义内的位置，不加 `source_id` 时两条释义的第 0 个标签会主键冲突。
